# 042 — A persona may write to the vault: drafts for new notes, staged edits for existing ones, delete only ever soft

> **Status: Accepted; Tier 1 built (2026-10-05, in ADRs 069 to 073).** Proposed 2026-09-29; amended 2026-10-04: proposals are tracked changes in the editor, see the Amendment below. What is built: her `propose_edit`, `propose_note` and `comment_on` tools (ADR 072), the store (ADR 070), the editor's tracked changes and Accept/Decline (ADR 042 amended, 069), the Drafts section (ADR 071), four modes per persona in which the file still changes only when the user clicks Accept or saves. **Not built:** a persona delete tool (the soft-delete design below is unused by her), and Tier 2, direct write, which is reserved and not designed (the user's rule is that no mode writes without Accept). This record, as first written, fills the gap ADR 040 explicitly left open ("the write question is a separate decision and not an extension of this one"), tracked as issue #21. Two tiers: Tier 1 (staged, this record's only built tier) and Tier 2 (direct, per-persona and per-folder, user-opt-in only). Each tier is gated on its own write-specific accuracy bar, not the 73–80% retrieval number ADR 040 measured — see "The bar is tier-specific" below; neither bar has been measured yet. Builds on the propose/write split already used for folder definitions (ADR 033/034) and the soft-delete-by-default mechanism the vault already has; distinguished from ADR 037's "hidden," which is a display preference, not a trust boundary.

## Context

The same conversation that produced ADR 041 also raised this directly (`profiles/samantha/sessions/20260928T151614-f2401cff.jsonl`, turns 14–15): asked whether she could write to the vault, Samantha said she can't create, edit, move, or delete anything — "your vault stays entirely yours" — and, told this is where things are headed, added "an assistant that can't touch your files is mildly inconvenient, but an over-eager one accidentally mangling your notes would be a nightmare... I'm happy to just be the sounding board while you hold the keys." ADR 040 reached the same conclusion independently, for a measured reason: grounding accuracy on real vaults is 73–80%, and "write tools (#21) need an agreed bar first."

The user's own framing of this record: it should still get built — "in the end, its still the user who will trust the persona" — the job here is to make sure the concrete safeguards are actually in place first, naming two by example: draft/publish states on notes, and reusing the existing bin so a persona is structurally unable to make a delete permanent.

What already exists, checked against the real code rather than assumed:

- **Deletion is already soft by default, and permanence is already a separate, deliberate action.** `vault_write_delete.py`'s `delete_note` never unlinks a file — it `os.rename`s it into `<vault>/.trash/<original relpath>`, preserving the path; a name clash is handled by `vault_trash_index.py`'s `.trash-index.json` sidecar. `vault_trash.py::restore` reverses this. A genuine permanent delete exists — `purge` (one note) and `empty_trash` (the whole scoped bin) — but it is wired to its own routes (`server_trash_handlers.py`), never a side effect of the normal delete path. This safeguard the user is asking for is therefore already true of every delete in the system today; the only thing a persona-facing delete tool has to get right is never being given a path to `purge` or `empty_trash`.
- **No draft or staged-edit concept exists for notes.** `vault_write.py` has exactly two operations: `overwrite_note` (replaces an existing note's content, with an `expected_mtime` concurrency check) and `create_note` (`vault_write_create.py`, refuses rather than overwrites). Both apply immediately, in place, to the live file. The word "draft" elsewhere in the codebase (ADR 033/034, `folder_definitions_write.py`) is a real precedent but a narrow one: a `Draft` dataclass is built in memory, shown, and only then written by a second call (`write()`) — genuinely propose-then-commit-on-approval, but held only across one synchronous CLI prompt, not persisted, and specific to folder-definition notes. It generalizes here; it isn't already general.

## Decision

**Access is layered, not a single on/off.** This record builds exactly one tier — **propose-only** — and reserves, without designing, a second:

- **Tier 1, propose-only (the only tier this record builds, and the only one that ships).** Nothing a persona does ever writes to the live vault directly. A create or an edit exists solely as a pending proposal until the user publishes it — draft mode is a guarantee that nothing hit disk under the persona's own action, not a label on something already written. This is the default and, until Tier 2 exists, the only option: not a setting a persona or a model tier can escalate out of.
- **Tier 2, direct write.** A persona writing live, with nothing staged first: a setting, `vault_write` (`staged` default, `direct` the opt-in), scoped per persona and, within that, **per folder** — a user can set `direct` for one folder (a Daily journal, say: low-stakes, additive, easy to fix by hand) while everything else the same persona can touch stays `staged`, the same way `vault_folders` already scopes read access per folder rather than all-or-nothing. `direct` is never a default and never earned automatically — not by a model's measured capability (unlike `vault_lookup` or `memory_rewrite`, ADR 040/041), not by usage, not by anything the system infers. It exists only if a user deliberately opts a specific persona (and, within it, specific folders) into it, and turning it on is its own explicit, spelled-out moment — the same shape ADR 031 already uses for `/share` — not a settings toggle flipped in passing. `direct` still routes through `create_note`/`overwrite_note` with their existing concurrency checks (`NOTE_EXISTS`, `expected_mtime`); it only removes the pending-queue step, not the underlying safety those functions already have. Delete's soft-only rule (1, below) is unconditional and is not something `direct` relaxes — it governs both tiers alike.

**Tier 1 is three tools, each safe by construction, not by a confirm step wrapped around an otherwise-unsafe action:**

**1. Delete — always soft, no new mechanism needed.** A persona's delete tool calls exactly `delete_note` (or the folder equivalent), the same move-to-`.trash` every human delete already goes through. `purge` and `empty_trash` are never called by, or reachable from, any persona-facing tool. "Permanently gone" stays what it already is today: a separate, deliberate action only the human takes, through the existing trash UI. This is the one Tier-1 action that touches a real file at all, and it already only ever moves it somewhere recoverable — nothing new to build beyond restraint in what the tool schema exposes.

**2. Create — staged, never written to the vault.** A persona's proposed new note is held as a pending entry (its intended path, its proposed content) in the same pending-changes queue as edits, below. No file is created by the persona's own action. **Publish** creates it for real, through the existing `create_note` (still subject to its own `NOTE_EXISTS` refusal, if something now occupies that path). **Discard** drops the pending entry — nothing to clean up, since nothing was ever written.

**3. Edit to an existing note — staged, never applied in place.** A proposed change to a note that already exists is held the same way: in `.pending-changes-index.json`, a single sidecar covering both creates and edits (told apart by a `kind` field), load-mutate-saved under the same file-lock discipline `vault_trash_index.py` already uses for its own index — mirroring that module's shape rather than merging into it, since trash and pending changes have different lifecycles. The live note is untouched throughout. The user is shown a diff between the current content and the proposal — the same plain-text, model-agnostic diff mechanism ADR 041 already committed to for `memory_rewrite: ask` — and either **Publish**, which applies it through the existing `overwrite_note` (its `expected_mtime` check still fires if the note changed in the meantime, exactly as it would for a human editor's conflicting save), or **Discard**, which drops the pending entry and touches nothing.

Together, this means Tier 1 performs exactly one kind of real filesystem action on the persona's own initiative — moving a note into trash, already the vault's own long-standing safe default — and zero others. Every create and every edit exists only as a proposal until a human, not the persona and not the system, commits it.

**Distinguished from ADR 037's "hidden."** Hidden is a per-vault display preference for content the user already trusts but doesn't want cluttering their view — that ADR's own design keeps it searchable, not walled off from grounding. A pending proposal is a trust boundary for content nobody has reviewed yet, and has to be excluded from grounding entirely, not merely deprioritized in a list. Reusing one mechanism for both would either weaken hidden's guarantee (a user's own decluttered notes start looking unreviewed) or wrongly exclude content the user never asked to distrust.

**The bar is tier-specific, not one number.** ADR 040 measured grounding at 73–80% on real vaults and left "agree a bar before agent write" as an open decision (`docs/CHECKLIST.md`); this record does not treat that as one threshold both tiers must clear:

- **Tier 1** is cheap to be wrong in — a bad proposal costs the user one Discard, no worse than any other mistake an assistant makes in conversation. The working view is that 73–80% is plausibly already good enough here, but that's untested against the actual task: today's number measures whether retrieval *finds* the right note, not whether the model *writes* a note or edit that stays faithful to it without adding anything ungrounded. That write-specific accuracy hasn't been measured at all, and needs its own pass — the same style ADR 040 used for tool-calling — before Tier 1 is called ready, whatever number it turns out to be.
- **Tier 2** has no review step to catch a mistake, so it needs a higher, separately-measured bar on that same write-specific accuracy, agreed only once Tier 1 exists to compare against.

Neither ships before its own bar is measured and agreed; this record settles what the safeguards look like once it is.

## Consequences

- New primitives, all Tier 1: `.pending-changes-index.json` (creates and edits, told apart by `kind`), its own lock-guarded module alongside (not merged into) `vault_trash_index.py`; a single "Persona changes" review queue shaped like `list_trashed` (scoped to `allowed_dirs`, an action that commits, an action that discards). No grounding-side filter for a draft frontmatter marker is needed, since a Tier-1 proposal is never a real note in the vault at all until published — it cannot be found by grounding, the vault map, or anything else that reads the filesystem, by construction, not by a flag it has to remember to check.
- The persona-facing write surface is exactly three tools — create (always staged), propose-edit (always staged), delete (always soft) — and none of them, ever, calls `overwrite_note`, `create_note`, or `purge`/`empty_trash` directly on the persona's initiative. Only the user's own publish action does.
- The web app needs one review surface for pending changes alongside its existing Trash view, since creates and edits now share one queue and one shape.
- This generalizes, rather than replaces, the propose/write split `folder_definitions_write.py` already uses (`Draft` dataclass, `draft()` then `write()` on yes): the same shape, made persistent and queue-based instead of held only across one synchronous CLI prompt, since a chat turn can't keep a write open across an entire review cycle the way a blocking CLI prompt could.
- `vault_write` (`staged`/`direct`) joins `vault_folders` as a second per-folder-scoped setting a persona carries, and needs the same explicit-consent screen `/share` already has before `direct` takes effect anywhere.
- No number ships in this record for either tier's bar. The next concrete step is a write-specific measurement (ADR 040's real-model-call style) once Tier 1 is built enough to measure against, covering both "does the write stay faithful to what was found" and, separately, whatever higher bar Tier 2 is later judged against.

## Amendment (2026-10-04): proposals are tracked changes in the editor, and the persona reads highlights and comments

A design talk replaced the chat card and the separate review queue with a collaboration surface inside the note's own editor. The safety shape above is unchanged: a Tier 1 create or edit is still only a pending proposal, nothing the persona does reaches the vault before the user accepts, and delete stays soft. What changes is where the proposal is seen and decided.

- **Tracked changes in place.** A proposed edit is drawn in the open note in a distinct colour, like a git diff: the replaced text struck through or highlighted, the new text beside it. The proposal is a patch (the passage quoted, and its replacement), not a rewrite of the whole note, so the diff is exact and nothing outside the quoted passage can change. Whether a small model can quote a passage reliably is the write-faithfulness measurement this record already requires.
- **Two levels of Accept and Decline.** Each persona edit and each persona comment carries its own Accept and Decline at the change. The editor toolbar carries a note-level Accept and Decline; accepting the note is what saves it to the vault, through `overwrite_note` or `create_note` as before, with the same `expected_mtime` and `NOTE_EXISTS` checks.
- **Turn-based.** The persona proposes in her turn and the user writes in his; she never types alongside him. The user may keep typing while a proposal is pending, and the proposal's ranges move with his edits. If he edits the very words a proposal changed, that one change is marked outdated (greyed, with a short note that the note changed there since it was written); he declines it or asks her to redo it. There is no automatic merge.
- **A Drafts section** at the top of the notes panel, directly above the notes list and the Pinned list, lists the notes with changes waiting for review. It replaces the "Persona changes" queue; it is built from the same shared section components as Pinned.
- **Working names.** A new note she proposes has no file name yet. It is listed under a working name of three to five words taken from what is already written in it: her own title in the proposal if she gave one (no extra model call), else the first heading, else the first five words. Accepting the note saves it under that name (sanitized; an existing note of that name is refused, as `create_note` already does). Once it is in the vault and still carries its working name, the persona asks in chat whether the user wants to rename it.
- **Highlights and comments.** The user can highlight a passage of a note and comment on it. They are kept out of the vault and out of the note's Markdown, in the persona's own data folder, because files the user did not create appearing in the vault would confuse. They travel with the user's next chat message as context, labelled new since the last message or earlier; the persona answers in chat and can reply under a comment; either side resolves a comment and it stops travelling. They are vault-derived, so they are a new `/share` category and a cloud model receives them only when the user has approved it. Their own record is a separate ADR.
- **Web app only.** Reviewing, accepting and commenting are editor surfaces and are not built for the terminal, which is not expected to create or edit notes. In a terminal chat the persona can say a change is waiting and point to the web app.
- **Stylo.** Custom toolbar buttons are supported today (the note-level Accept and Decline). The inline marks, per-change buttons, margin markers and comment popovers are not in stylo's public props; stylo exposes the CodeMirror view through `getView()`, an escape hatch with no stability promise. A spike checks that extensions added to the live view coexist with stylo's in-place canvas; a lasting version needs a capability request to stylo, written as a document, since stylo is not edited from here.

**Amended again (2026-10-04, ADR 072):** the reserved second tier (direct writing, per persona and per folder) is not pursued: in every mode the user has the last say by clicking Accept. How much she does before that is the user's choice among four modes (plan, manual, accept, auto), set out in ADR 072.

## Open questions

- **The write-faithfulness bar, Tier 1.** First measurement made (see Measured, 2026-10-04); the bar itself is still for the user to agree. A larger set of notes and a second small model are the open part.
- **The Tier 2 bar and consent screen.** Higher and later; the shape of the consent screen follows `/share`.
- **Extensions on a live stylo view.** Whether decorations, widgets and a gutter added through `getView()` survive stylo's in-place decorations, undo, scroll and both `in-place` and `source` modes, or the feature waits for a stylo hook.
- **Keeping proposals out of search, the nebula and the map.** A pending proposal is held in the persona's data folder, not in the vault, so it cannot be found by anything that reads the vault; confirm this holds for the Drafts listing and for a note that exists only as a proposal.
- **How a pending proposal is stored and keyed** (by the note's vault path, with the text it was written against so an outdated change can be detected), shaped like `vault_trash_index.py`, and which API the editor and the Drafts section read.
- **How a proposal is requested in chat** and whether it is a tool call in the `vault_lookup` loop (ADR 040) or a structured part of the reply.

## Measured (2026-10-04): how faithfully a model edits a note

`tests/live_patch_cases.py`, on invented notes only (nothing of anyone's vault), nine requests (change a phrase, add a bullet, fix a typo, edit a line that appears twice, keep a wikilink, delete a bullet, a formal rewrite, add a section, and a request that needs a fact the note lacks) asked four times each in three shapes: a JSON patch (the passage to find and its replacement), SEARCH/REPLACE blocks, and the whole new note. A reply is scored by applying it: the passage must be found exactly once, and the resulting note must be what was asked with nothing else changed and no invented fact. 36 replies per cell, so every figure is about that model and this set only.

| Shape | `gemma2:9b` correct | applied but wrong | Gemini Flash correct |
|---|---|---|---|
| JSON patch | 29 of 36 | 2 | 36 of 36 |
| SEARCH/REPLACE | 27 of 36 | 1 | 36 of 36 |
| Whole note | 27 of 36 | 9 | 32 of 36 (all four are a correct refusal the scorer read as a note) |

- **A patch fails in the open.** The small model's misses in the two patch shapes are mostly a quoted passage that could not be applied: a line that appears twice (0 of 4 in both shapes) and a new section anchored on the prompt's own end marker (0 of 4 in blocks, so a framing marker must not look like note text). The app can refuse such a patch and say so; nothing is changed. A whole-note rewrite that is wrong looks like any other rewrite: 9 of 36 replies were applied and wrong or unchanged, against 1 or 2 for a patch, which is the case for patches.
- **Invented facts.** Asked for the exact price of the tomato seeds, `gemma2:9b` wrote a price into the note in 1 of 4 JSON replies while its own sentence said it needed the price. Gemini Flash made no change and asked for it, 4 of 4. A change that invents text is exactly what Accept and Decline is for, and it is a reason a proposal should show the model's own sentence beside the diff.
- **One more mode in blocks.** Deleting a bullet by replacing it with lines already in the note duplicated them in 1 of 4 replies.
- **Reading.** For Tier 1, where a bad proposal costs one Decline, a patch from a small local model is workable (about 80 percent correct here, most misses refused rather than applied); a cloud model had no miss. The Tier 2 bar, with no review, is not met by 80 percent and was not the question here.

## Alternatives rejected

- **Writing a persona-created note directly to the vault immediately, flagged only by frontmatter as a draft** — this record's own first draft. Rejected: a real file on disk, excluded from grounding only by a flag the retriever has to remember to check, is still a write, and "draft mode" stops being a guarantee and becomes a convention that something else could bypass. Staging creates exactly like edits, so nothing touches the vault until publish, makes Tier 1 safe by what it structurally cannot do, not by what it's asked not to do.
- **Confirm-in-chat before every write, as the sole safeguard** (ADR 040's "ask" shape, applied literally per write). Rejected as the only mechanism: it reintroduces a blocking round trip on every single note action, against the project's founding low-round-trip motivation, and fits poorly with a persona that might reasonably produce several notes from one conversation. Staging lets the proposal happen fluidly and the review happen in bulk, at the user's own pace, while still requiring an explicit human action before anything becomes live.
- **Reusing ADR 037's hidden-folder mechanism as the staging mechanism.** Rejected above: hidden and unreviewed are different guarantees, and collapsing them weakens one or misapplies the other.
- **Giving a persona's delete tool a path to `purge`, gated by a confirm step.** Rejected: today's delete is already safe by default (soft, recoverable), with permanence requiring its own separate, deliberate human action. Adding any persona-reachable route to that action, confirmed or not, is strictly more risk for no benefit — nothing a persona does ever requires permanently destroying a note.
- **Letting model capability (ADR 040/041's tiering axis) decide access to Tier 2.** Rejected: a strong model being good at writing faithfully says nothing about whether the user wants to be bypassed on this particular persona's output. Tier 2 is a trust grant, not a competence threshold, so it's gated on the user's own explicit choice, never inferred from what a model measures capable of.
