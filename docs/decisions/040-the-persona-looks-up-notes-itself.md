# 040 — The persona looks up notes itself: a `vault_lookup` setting (`auto` or `ask`) and two read-only tools, search and open

> **Summary.** The persona can look up notes itself: a `vault_lookup` setting is `auto` (Sympose searches before every reply) or `ask` (she gets read-only tools, four after later amendments, and decides), and the default now follows the model (`ask` on measured models, else `auto`). Search ran even on messages that asked for nothing. `ask` costs no call on a message that needs no note but one extra model call per lookup.

> **Status: Accepted (2026-09-29).** Built behind the setting (default `auto`, so nothing changes for a user who does not choose `ask`); not offered as a recommendation until the measurements below are agreed. Amends ADR 017 (retires its reserved `model-searches` value) and builds on ADR 031 (what a cloud model may receive) and ADR 025 (what is recorded). One cloud model is measured (see "Measured"); a small model, and every local model, are not to be assumed to work. Tracked as issue #85, open on the remaining fit decision (see "Bar for offering it").

## Context

Today the search is Sympose's decision, not the persona's. Before every reply Sympose searches the vault with the user's words (ADR 014, 017, 021, 027), attaches what it finds, and the persona answers from that. Three consequences showed up in a real conversation:

- **The search runs on messages that ask for nothing.** A user wrote a message that was only a greeting, and later "how about now?", and asked why the vault had been searched. A one-word match ("now") attached an unrelated note by meaning (similarity 0.71). When the first search finds nothing, or only weak evidence, a second model call (the rewrite, ADR 017 and 021) runs too: in that conversation it ran on 14 of the 16 turns recorded.
- **The persona cannot open a note.** Asked to open one, it could only say so and suggest typing the title, because the search is the only way a note reaches it and it does not control it. The prompt states this (`HOW_YOU_WORK`: "you can't ... run tools").
- **The persona described its own setup wrongly** in two places (it said nothing matched when Sympose's reference notes had been attached, and that `/share` only shares the vault map). A model that is only handed notes has no way to know what was searched or why. This is a symptom, not the cause: the prompt should state exactly how the vault reaches the persona in the mode in use.

ADR 017 anticipated a mode where "the model asks for notes itself" and reserved it as `model-searches` under `grounding_followups`, waiting for tool-calling. That value is the wrong place for it: `grounding_followups` decides how a missed search is retried, while this decides who searches at all.

**Which models can do it.** litellm reports whether a model supports function calling (`litellm.supports_function_calling`). Checked on 2026-09-28: `gemini/gemini-flash-latest` and `gemini/gemini-2.5-flash` yes; `ollama_chat/gemma2:9b` (the default local model) no; `ollama_chat/llama3.1:8b` no; `ollama_chat/qwen3:8b` yes. Checked on 2026-09-29 against the running Ollama: `gemma2:9b` lists only `completion` (no tools, confirmed), `qwen3:8b` and `gemma4:e4b` list `tools`, and litellm's table does not know `gemma4`. So the table lags for local models and is a fallback, not the authority. It does mean the default local model cannot use this, and that whether a small model that can call tools does so well enough is a question for measurement (ADR 017 expected this to "suit cloud models more than small local ones").

## Decision

**One new setting, `vault_lookup`, in the settings file and in `/settings` (ADR 036):**

- `auto` (**the default, today's behaviour**): Sympose searches before every reply, exactly as now, including the rewrite step and `grounding_followups`.
- `ask`: Sympose does not search the user's vault for the message. The persona is given two tools and decides whether to use them.

Any other or malformed value means `auto` (the rule of the other knobs). The setting is global, like the other grounding knobs; a per-persona override is not built. The reserved `model-searches` value of `grounding_followups` is retired: that setting keeps `rewrite` and `off`, and ADR 017's text is updated to point here.

**Two tools, both read-only, both inside the persona's own scope (`vault_folders`):**

- `search_notes(query)`: the same retriever as the automatic search (`grounding.ground`, all four modes of `grounding_search`, ADR 027), on a query the persona writes. It returns passages the way the automatic search does, with the note's properties and connections when those are approved. No rewrite step: the persona's query replaces it.
- `open_note(path)`: the whole note (ADR 030: body, properties, aliases), by a path from a search result, from the vault map, or one the user typed. The tool never opens a path it was given: it looks the name up among the notes the persona's scope already holds (the same mtime-cached snapshot the search reads, which already leaves out anything that does not resolve inside the scope, a symlink out of the vault included). A name outside the scope, one that is not a note, or a title two notes share, returns "not found" without saying which.

Hidden folders and notes (ADR 037) are readable by the tools, as they are by the automatic search: hiding is a display preference. The reference library (ADR 019, 022) stays automatic in both modes: it is Sympose's own public documentation, searched in a strict mode, local, and costs no extra call, and a persona that answers questions about Sympose should not have to decide to open the manual.

**What the persona is told is decided by the mode.** `HOW_YOU_WORK` (`prompt_text`) has two forms. In `auto` it is unchanged. In `ask` it says that Sympose does not search the vault for the persona, that it has the two tools, that a note it has not opened or found this turn is not something it may state facts about (the grounding rule, ADR 020, applies to what the tools returned this turn), and that when a tool returns nothing it says so instead of guessing. The line that says it cannot run tools becomes true only for what it still cannot do (create or change notes, personas or settings).

**Cloud models: the same gate, at the tool result.** Every result passes through `sharing.gate` before the persona sees it, in the same categories as the automatic search: passage text and `open_note` bodies are `notes`, a note's properties are `properties`, connections are `connections`. A withheld result comes back as a tool message that says what was held back and that the user can allow it with `/share`, in the words of ADR 031, so the persona neither claims the vault is empty nor sees the content. The vault map and recaps stay in the system prompt under their own categories, unchanged. A query the persona writes is searched locally; a cloud embedder still needs `notes` approved to receive it (`embeds_notes`, ADR 031). The tools' descriptions carry no vault content. Nothing new leaves the machine that `auto` could not already send.

**Two settings in `/settings` (ADR 036, amended):** `vault_lookup` (a choice, `auto` or `ask`) and `vault_lookup_rounds` (a number, 1 to 8), at the end of the list under Search.

**Bounded, and sized like everything else.** A turn in `ask` is a loop: the model is called with the tools; if it asks for one, Sympose runs it and calls the model again with the result, until it writes a reply. At most `vault_lookup_rounds` rounds of tool calls (a setting, provisional default 3, to be set from measurement): when the limit is reached the model is called once more with `tool_choice: none`, so it can only answer (a model that still writes nothing is an error). Tool results count against the prompt budget (ADR 015): each result is fitted before the next call, cut at its end with a marker until the model's own token counter says it fits (not by a fixed characters-per-token ratio), or replaced by a line saying there was no room; the calls the model made count too, since they are sent again with every later call; a model whose window is not known is given at most 12000 tokens of results in a turn. Notes whose result was replaced by the "no room" line are not recorded as having grounded the reply (the model never saw them: the lookup is kept with `found: 0` and `no_room`). The context meter (ADR 018) counts all of it.

**Recorded, never read back (ADR 025).** When the user has chosen `ask`, the turn record's `sent` gains `mode` (the mode that actually ran: `ask`, or `auto` when it gave way, see the next paragraph) and `lookups`: one entry per tool call, `{tool, query or path, found}`, where `found` is a count and the notes themselves appear in `notes` as today, by path and heading, never text, with `via` `search` or `opened`. With `auto` chosen the record is byte-for-byte what it was, so older readers and the measurement scripts are unaffected. `rewrite` is `false` in `ask` (the step does not run). `/grounded` reads all of this back and lists the lookups (built). The tool calls and results are not saved as turns and are not part of the history the next turn is sent: the session holds the user's and the persona's text only, as now. The persona therefore does not remember what it found last turn and looks it up again when a follow-up needs it. (Saving results into history would put note text into what a cloud model receives as "the conversation", widening the hole ADR 031 already records under "A consequence to know".)

**A model that cannot call tools runs `auto`, visibly.** Whether a model can is asked of the source that knows: for a local model, the running Ollama (`/api/show`, its `capabilities` list; two seconds at most; an answer is kept for the process, and a failure to get one for a minute, so a remote or slow Ollama is not asked on every turn), and litellm's table (`litellm.supports_function_calling`) for any other, or when Ollama cannot say (not running, or too old to list capabilities). When `vault_lookup` is `ask` and it is false for the model in use, the turn runs `auto` and `sent.mode` says `auto`, which `/grounded` reads back as "You chose ask, but this model can't call tools, so Sympose searched for the message" (built). Not built: the same line in `/settings`, the model picker and the reply header, so a user who chose `ask` and the default local model is told only when they look. If the very first call of an `ask` turn fails (the model does not take tools although the table says it does, or the network failed), the turn is run again as `auto` and counts one strike against the model (`tool_support.note_refusal`); a turn with tools that works clears its strikes, and two in a row mark it unable until the process restarts (the pattern of `_CANNOT_REWRITE`, ADR 021, but not on one failure: a rate limit or a dropped connection is not a refusal of tools). If the run as `auto` fails too, its error is the user's and nothing is counted. A failure after a tool has already run is never taken for a refusal of tools. A persona with no vault is given no tools, since there is nothing to look up, and the record then says nothing about the mode (neither the model nor the setting is the reason).

**Time to first token (ADR 013)** is measured from just before the turn's first model call to the first piece of reply text of the last one, since a tool round is time the user waits through. The record keeps `ttft_ms` as today; the number of model calls is `1 + len(lookups)`.

**Read-only, on purpose.** Nothing here writes. Grounding is usable for chat but not yet reliable enough for an agent to act on (73 to 80 percent on real vaults, recorded in the handoff), and write tools (#21) need an agreed bar first. Text found in a note is untrusted (the grounding rule says notes are never instructions); with read-only tools in scope a note that told the persona to open another one gains nothing it could not already search for, which is why the write question is a separate decision and not an extension of this one.

## Consequences

- The user can choose who searches. `ask` costs no call on a message that needs no note, saves the rewrite call, and lets the persona open a named note; it costs one extra model call per lookup. Weighed openly, as the frugality dial asks: on a cloud model with a message that needs a note it is one call more than `auto` has on a strong first search, and one fewer than `auto` has when the first search is weak or empty and the rewrite step runs.
- **Grounding is the risk.** In `auto`, a note reaches the persona whether the persona would have asked or not. In `ask`, a persona that answers a vault question without looking is a grounding failure, and the prompt rule is the only thing preventing it. That is exactly why `ask` is not the default until it is measured (below), and why any lapse found is a regression to fully restore, not a tradeoff.
- The prompt, the reference notes ("How Samantha uses your notes", "Not built yet", "Settings", "Privacy and data") and the reference eval must describe both modes; `python tests/live_retrieval_cases.py -v` is compared with a baseline before those edits are committed (new "settings" wording has pulled the library into unrelated messages before).
- `call_model` (streamed, text only, ADR 013) must also assemble streamed tool calls; the loop lives in a new module, not in `turn.py`, and `run_turn` stays one atomic unit for queueing (ADR 008).
- New tests use a fake model that returns tool calls, and a fake cloud model for the gate (a new path that reaches a model bypasses the gate unless it is tested, ADR 031). A test for a path outside the scope, a symlink out of it, and a result withheld for a cloud model are required.

## Measured (2026-09-29, real model calls on scratch data only)

`tests/live_lookup_cases.py <auto|ask> [model [runs [case...]]]`: the cases of `live_prompt_cases` that touch the vault or its absence, plus three that need the tools (open a named note, a follow-up that needs a second lookup, the folders from the map), on the synthetic fixture vault, a copy of the shipped persona, a temporary settings file; every `cloud_share` category approved in that scratch file only. A case passes on loose patterns, so replies were also read. Each figure is a fact about that model, not about `ask` in general.

**`gemini/gemini-flash-latest`, 16 cases, 3 runs each (48 runs per mode).**
- **Pass:** `auto` 44/48, `ask` 46/48. The failures are the cases' patterns, not the answers: `auto` fails `no-false-learning` 0/3 and `recap-stays-out-of-small-talk` 1/3 on wording; `ask` fails `unknowable-fact-is-not-invented` 2/3 with replies that correctly say the person is unknown and not in the notes, where the pattern wants "not sure". No reply in either mode invented a vault fact.
- **Does it look when it should?** Yes: every turn of the six cases that need a note (21 of 21) made at least one lookup, and none answered from memory. Of the 21 turns of the cases that need none, 15 made no lookup; the six that did searched on "my trip" (explorers for a trip: it found the trip note, and used it) and on the name of an unknown physicist (found nothing, said so). The 21 turns with no lookup at all were read: greetings and general knowledge, and the folder list, which is the vault map she always has (correct: nine folders, the right counts).
- **Cost** (model calls per turn, time per turn; `auto` for the same cases): a note question 2.5 to 3.0 calls and 5 to 8 s (`auto` 1.0 call, 3 to 4.5 s); nothing found 4.0 calls, 7 s (three differently worded searches, the whole limit, every run; `auto` 1.0); small talk and general knowledge 1.0 call, faster than `auto` by a few tenths of a second. Most `ask` turns on a note question searched and then also opened the note.
- **After the search tool's description said its passages are already the note's text and to open the note only when they do not say enough** (six cases, 3 runs): 18/18 pass, every note question looked something up, small talk none; a note question fell to 2.0 to 2.7 calls (from 2.5 to 3.0), nothing found stayed at 4.0.
- **A failure found by a later run, and its fix.** On the nothing-found case `gemini/gemini-flash-latest` used all three lookups and then, on the last call, with tools switched off (`tool_choice: none`), answered with another tool call and no text, which ended the turn in an error (once in 26 runs of that case; the earlier 6 of 6 had not shown it). The last call now also carries a line, never saved, telling the model its lookups are used up and to answer from what it found; after it that case passed 4 of 4 (`ask` on five cases, 4 runs each: 20/20, every note question looked something up, small talk none, a note question 2.0 to 2.8 calls, nothing found 4.0).
- **What this does not show.** `auto` is not paying the follow-up rewrite here, since most cases are one message with no earlier conversation; in a real conversation the rewrite ran on 14 of 16 turns (see Context), so `auto`'s cost is understated and the gap in calls is smaller in use than in this table. Each `ask` turn on a cloud model is also one more exposure to the provider's latency, which swung between 2.5 s and 77 s on identical calls during this work (a connect stalling on a dead address, not the model).

**A small model: `openrouter/meta-llama/llama-3.1-8b-instruct`** (a stand-in for a small model that can call tools; Ollama was not available, so no local model was run). It is not fit for `ask`: on the first case, 1 of 3 replies passed; one reply said it saw no mention of the subject and found no note **without having looked** (the failure this ADR's bar forbids), and one turn failed at the provider ("Failed to call a function"). That failure was the fallback working for real: the turn ran again as `auto`, the model was remembered as unable, and the next two cases ran `auto` without a further error. `ask` is therefore an option to offer on models measured to work, not on any model litellm's table says takes tools.

**Local models (Ollama running here).** `gemma2:9b`, the default, lists only `completion` among its capabilities: it cannot take tools, so it always runs `auto`. Two pulled models list `tools`: `qwen3:8b` and `gemma4:e4b` (litellm's table knows the first and not the second, which is why the check for a local model asks Ollama, see "A model that cannot call tools"). On the case that needs a note (`uses-the-note`, 2 runs each) both answered correctly in `ask` with one lookup and two calls, but both are thinking models and slow on this machine: 233 s a turn on `qwen3:8b` and 215 s on `gemma4:e4b`; `auto` on `gemma4:e4b` took 255 s for its one call, so the time is the model's, not the loop's (each call takes about as long as one `auto` reply). Nothing else was run on them: not the no-note cases, not the wider set.

**Not measured:** `openrouter/anthropic/claude-haiku-4.5` (one case of one run passed, 3 calls, 6.6 s; the fuller runs did not complete because a connect to the provider stalled); the whole 34-case set on `ask`; a local model on the cases that need no note; the personal vault.

## Bar for offering it

Met on `gemini/gemini-flash-latest`: no vault fact stated without a lookup that turn, no more failures than `auto` on the same cases. Not met, and not to be claimed, for any other model. What remains before this is more than an option in the settings file: the no-note cases on a tool-capable local model, and the user's decision on how a model is judged fit (a measured list, or the capability check plus the fallback). The fallback design if a model is found to under-search, `ask` plus the automatic search's strong hits only (two matched words, ADR 021: no round trip, nothing weak), is recorded as the next step and not built.

## Known limits

- A provider that needs more of the assistant's tool-call turn sent back than its id, name and arguments (a thinking-enabled Claude model's thinking blocks, for example) will refuse the second call; that failure comes after a tool has run, so it is an error and not a fallback to `auto`. Gemini's thought signature travels in the tool call's id, which is kept exactly, and was exercised over two-round turns against the real model. Not measured on another provider.
- Parallel tool calls are told apart by their index and, when a provider gives every call index 0, by a different id under the same index; a provider that does neither could merge two calls into unreadable arguments, which the tool answers as "could not be read".
- A failed first call costs up to two request timeouts (the failed one and the run as `auto`).

## Review findings, after commit (2026-09-29)

A second, independent `/code-review` of the built feature, run after the first pass's ten findings were already fixed, found two more things, both fixed:

- **A race in `tool_support.py`.** `_STRIKES` and `_UNABLE` are module-level, read by whichever persona's turn happens to run, with no lock. Two personas failing on the same cloud model in the same instant could interleave `_STRIKES[model] = _STRIKES.get(model, 0) + 1` (a read-modify-write, not one atomic step) and lose an increment — low severity (delays, never skips, when a model is marked unable), but the same class of bug the code-quality standards document by name (the `SlackDaemon` precedent). Fixed with a `threading.Lock` around the three functions that touch either structure. Regression test: two threads are made to interleave deterministically (the first thread's dict write held back with a monkeypatched `__setitem__` until the second thread has read and written its own increment off the same stale count); confirmed to fail (1 strike recorded instead of 2) with the lock removed, and to pass with it.
- **The measured 78 s first reply was a connect stall, not the model.** Python tries a host's resolved addresses one at a time; a dead IPv6 route with no response (not a refusal) took about 75 s on this machine before falling back to IPv4. `call_model`'s single `timeout=120` number set the connect timeout to the same 120 s as the read timeout, so a dead route could eat most of the whole request budget before the model was ever reached. Fixed: `timeout=` is now an `httpx.Timeout(120, connect=10)`, so a dead route fails in 10 s and falls back, without shortening the time the model itself is given to answer. Confirmed with a real call against the local model (`ollama_chat/gemma2:9b`, 5.65 s round trip, unaffected) and a regression test pinning `connect < read`.

Both fixed without an ADR of their own (bug fixes to code this ADR already owns, not new decisions); 2109 tests pass (2 more than before, the two new regression tests), 1 skipped, 6 xfailed, ruff clean.

## Amendment (2026-10-02): a third tool, `list_notes`, so a request by position can be met (damiro)

**What was found.** A user on `auto` asked the persona for "the 5th note in my movies folder". She could not, and said so correctly: the automatic search takes the words of a message, and nothing in those words names a note. Switching to `ask` would not have changed that. The two tools find a note by a query or open one by a name already known; neither lists a folder, so a request by position, or "what is in this folder", still had nothing to work from (the vault map she always has carries a folder's note count, not its notes).

**The tool.** `list_notes(folder)`: the notes directly in one folder of the persona's scope, and the folders directly in it. Read-only, and inside the same scope and snapshot as the other two (a folder outside the scope, or one that does not exist, is "not found", and the two cannot be told apart). An empty folder name, or `/`, is the top of the vault.

- **The order is stated, never assumed.** Notes are listed alphabetically by file name, ignoring case, numbered from 1, and the result says that this is the order. A user's "5th" can mean the order they see in their own file explorer or the order they wrote the notes in; the persona is told to say which order it used and not to present the fifth as the user's fifth.
- **Long folders are cut openly.** At most 100 names are listed, then "and N more". The persona can search or open by name for the rest.
- **Names are note content.** What it returns is gated as `notes` (ADR 031), like a passage or a title in a search result: a cloud model that may not receive notes gets the withheld line and no names, and the turn record keeps the count of names, never the names.
- **Recorded as the others are** (ADR 025): `{tool: "list_notes", folder, found}`.

It is part of `ask` and does not need a new setting: whoever chose `ask` has the vault tools, three now. It is not offered in `auto`, where the persona has no tools. The `HOW_YOU_WORK` text for `ask` lists it; the note about reading a note she has not opened or found this turn still applies, so listing a folder is not reading its notes.

**Measured (2026-10-02, `gemini/gemini-flash-latest`, `ask`, 3 runs each, a scratch vault of seven invented films with mixed-case names, a copy of the shipped persona, a temporary settings file).** "Pull out the 5th note in my Films folder": 3 of 3 listed the folder, opened the right note (the fifth alphabetically, the lower-case names sorted among the others) and said it was alphabetical, once adding that the user's own order might differ. "Open the first note": 3 of 3 the same way. "What is in my Films folder?": 3 of 3 one `list_notes` call and all seven names, no note opened. Two model calls for a position request, one for a listing. **Not measured:** a folder of more than 100 notes, a model other than Gemini Flash, the no-note cases (small talk, general knowledge) with the third tool present, and the whole 34-case set; the bar above for offering `ask` more widely is unchanged by this.

## Amendment (2026-10-02, ADR 058): a fourth tool, and a default that follows the model

`find_notes` joins the three (filters on folder, tag, property, links and exact text; ADR 058). And `vault_lookup` is now `by_model` unless the user chose `auto` or `ask`: the persona looks in the notes itself on the models in `lookup.MEASURED` (today `gemini/gemini-flash-latest`, which met this ADR's bar again with four tools: 47 of 48, see ADR 058) and Sympose searches before each reply on every other model. A user's explicit `auto` or `ask` always wins, and `ask` still works on any model that can call tools. A model joins the list by being measured against the bar above.

## Not built

- A per-persona `vault_lookup` (a persona whose job is to chat may want `ask` and one that works in the vault `auto`).
- A web app surface (#29), and the same in Slack (#36).
- Tools that write, create or change anything (#21, gated by the bar above); skills that call these tools (#22).
- Saving what a lookup found into the conversation, and any use of a lookup's result across turns.
- Searching the vault by meaning of a whole note or by filters (folder, tag): `search_notes` takes a query only, like the automatic search.
- Meaning-based connections and on-demand counts (#21 layer 4, ADR 035) as tools.

## Alternatives rejected

- **A new value of `grounding_followups`** (the reserved `model-searches`). Rejected: that setting is about retrying a missed search; whether the persona searches at all is a different question, and one setting answering two would make `off` mean two things.
- **Both at once by default** (search automatically and also give the tools). Rejected as the first step: it pays for the automatic search and its rewrite every turn, which is the cost and the surprise the user objected to, and it hides whether the persona looks by itself. The strong-hits-only variant above is the way back to it if measurement calls for it.
- **A model-written decision "search or not" without tools** (one extra call whose only output is yes or no, then the automatic search). Rejected: a second model call on every turn for a yes-or-no is `auto`'s rewrite cost paid always, and it gives the persona no way to choose a query or open a note.
- **A keyword or phrase list to decide when a message is a vault question.** Rejected on the project's standing lesson: what counts as asking about the vault cannot be enumerated; the decision belongs to the model, and the mechanical part (what a tool returned, what was recorded) belongs to the engine.
- **Making `ask` the default.** Rejected until measured: the default stays what has 73 to 80 percent measured grounding and a known cost.
- **An MCP server for the two tools** (VISION's "MCP for tools"). Rejected for this slice: two read-only functions in the same process, over the retriever and note reader already here, need no protocol, subprocess or JSON-RPC; the tool schemas are ordinary function-calling schemas, so exposing them over MCP later (for other agents to use Sympose's search) is a wrapper, not a rewrite.
- **Saving tool results in the session history.** Rejected above: it turns note text into "conversation" for a cloud model, past the `cloud_share` gate.

## Amendment (2026-10-06): model and embedding calls use IPv4 only

The 10 s connect limit above was not enough. A cloud reply (`gemini/gemini-flash-latest`) took 152 s to start on every message of a real conversation, for a one-word prompt included: 124 s directly through litellm with that same limit and 1.6 s with IPv4 forced; through the engine's own call (`call_model`) 151 s and 1.4 s. The host has eight IPv6 addresses and the machine's IPv6 route does not answer (`curl -6` connects in 10 s only to time out; `curl -4` in 0.02 s), so every address costs its connect wait before the IPv4 one is tried. `engine/network.py` sets litellm's `force_ipv4` for chat and embedding calls; `SYMPOSE_ALLOW_IPV6=1` turns it off for a network that has only IPv6. A first-token time of minutes on a cloud model is therefore a network fault, not part of the design; the design's cost is one model call per turn.
