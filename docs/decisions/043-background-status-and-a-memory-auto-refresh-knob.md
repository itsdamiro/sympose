# 043 — An animated status line for background work, and a knob so memory refresh doesn't fight a real reply for the model

> **Summary.** Automatic memory refresh is off by default behind a `memory_auto_refresh` setting, and background work gets an animated status line. A real session showed the refresh competing with a reply for the model, so a reply took an uncomfortable amount of time. `/memory refresh` still runs it on demand.

> **Status: Accepted, built (2026-09-29).** Built: `memory_refresh.AUTO_REFRESH_SETTING` (`memory_auto_refresh`, off by default), gating the automatic `engine.refresh_memory` calls at launch and persona switch that ADR 041 added; `sympose/cli/background_status.py` (`BackgroundStatus`, a new animated line between the transcript and the composer) replacing the old far-right "indexing NN%" notice that used to live on the meter's own line (ADR 027); `sympose/engine/status_phrases.py`, a persona's own short witty status phrases, generated once from its soul the first time it is used and cached, with a generic fallback until then. `meter.py` is trimmed back to just the context bar. Live-verified against `gemma2:9b` throughout. `/code-review` (fork, high) on the built mechanism found two real issues, both fixed: `BackgroundStatus` only re-picked its phrase when the *kind* of activity changed, not when the persona did, so a switch landing on the same kind (e.g. both personas' launches starting a recap refresh) kept showing the previous persona's own phrase under the new persona's name — fixed by keying on `(handle, kind)`; and `activity()` never reported `status_phrases`' own generation call, which fires unconditionally at launch/switch and can itself contend for the local model exactly like `refresh_memory` did — fixed by adding `status_phrases.is_running` to the same check, closing the one background call this record's own busy indicator could not have shown itself running. A follow-up fix the same day: the composer kept a leftover top margin from before `BackgroundStatus` existed (`.composer-spaced`, toggled on whenever no picker panel was open, from the days the bare transcript sat directly above the composer) — it read as a gap between the new status line and the input it's meant to sit "directly above," so the toggle and its now-obsolete CSS rule were removed outright; the composer's top margin is simply 0 now, panel open or not. **Amended 2026-09-30 (see below):** the busy indicator now also covers the reply itself being generated — searching, reading a note, or asking the model — not just the four background jobs; damiro noticed it stayed silent for the entire wait on a real reply, the one wait most turns actually spend their time in. A same-day second amendment: a real phase running past 3 seconds now alternates with the persona's own witty line every 3 seconds, so a slow moment reads as active rather than frozen.

## Context

Right after ADR 041's `memory_rewrite` shipped, a real session (`profiles/samantha/sessions/20260929T115144-17e87c51.jsonl`) showed the exact failure mode a good measurement should have caught first: the user reported a reply taking "an uncomfortable amount of time" and a message showing as queued. Reading the session logs and file timestamps side by side (`profiles/samantha/context.md.bak`/`profile.md.pending`, both written 19 seconds after that session's launch) confirmed the cause: `app.py`'s `on_mount` now fires *two* background model calls at launch instead of one — `refresh_recaps` (already there, ADR 023) and the new `refresh_memory` (ADR 041) — both competing for the same local model a real first message needs. `recap_refresh.py`'s own docstring already accepts this cost for *one* background call ("the turn would queue behind it on a single GPU regardless, measured, ADR 023"); stacking a second one on top of it was not re-measured before shipping, and the user hit it on the very first real session with the new code.

A second session from the same stretch (`20260929T114041-57bf0c37`) showed a related but distinct problem while diagnosing the first: even once `context.md`/`profile.md` genuinely held content (`sent.memory` confirms it was sent), the persona still described her memory as session-only and vague ("I don't have access to past conversations... unless you share it with me here"). That's a real correctness gap, not a timing one — tracked separately, not fixed by this record (see "Not fixed" below).

Talking through the timing fix, the user's first instinct was a blocking loading bar at launch covering all the "preliminaries." Rejected on the spot: `recap_refresh.refresh_in_background`'s own comment says "background, while the user types" — ADR 023 deliberately chose not to block launch on a background job, the one thing the legacy blocking `rich.prompt.Prompt` loop couldn't do (VISION, lines 46-50) that this whole Textual rewrite exists to fix. A universal wait on every launch, even the overwhelming majority where nothing is slow, is a worse trade than the occasional slow first reply it would prevent.

What the user actually wanted, once we talked it through: (1) a knob, since neither of us was sure what the reasonable default should be, and (2) visibility — "the long time waiting makes it feel like there's something wrong with the app" — specifically an animated line above the composer, "the one you're having while doing something in the background," i.e. a spinner-plus-verb busy indicator like the ones coding-agent CLIs already use, with a small animated icon on the left. The witty phrasing was asked to be persona-flavored, not a fixed generic list, "generated when the persona is created" — surfaced as its own design question below, since Sympose has no persona-creation step to hook that into.

## Decision

**The knob: `memory_auto_refresh`, off by default.** `engine.refresh_memory` at launch (`app.py`) and persona switch (`runtime.py`) is now gated behind `memory_refresh.auto_refresh_enabled()`. Off restores exactly the pre-041 contention profile (`refresh_recaps` alone); `/memory refresh` bypasses the gate entirely, since running it is then the user's own explicit action, not something firing on its own. The default is off, not on, for a reason specific to this job and not shared by recaps: a recap is worth writing essentially every session (there's always new conversation since the last one); `context.md`/`profile.md` are explicitly designed to "change rarely" (ADR 041's own words) — there is much less to gain from checking on every single launch, and now direct evidence it costs something real when it does run at the wrong moment.

**The status line: `background_status.py`, replacing the meter's old far-right notice.** A new `Static` widget, `BackgroundStatus`, sits between the transcript and the composer — the one place the user is already looking right before typing, not tucked below the box where the meter's own line already lives. It shows a Braille spinner (`⠋⠙⠹⠸⠼⠴⠦⠧⠇⠏`, the same animation family most terminal busy-indicators already use, ticking every 120ms) followed by a short phrase, while exactly one of four things is running: a recap refresh, a memory rewrite, a persona's own status phrases generating for the first time (see below), or the search-index build (`semantic_refresh.progress()`, ADR 027 — indexing also gets its percent appended, since that's genuinely informative in a way the others' own progress isn't). When more than one is running at once, one is shown, not all four: recap, then memory, then phrase generation, then indexing — the order a new session's own background work naturally finishes in. `recap_refresh.py`, `memory_refresh.py` and `status_phrases.py` each gained a small public `is_running(handle)` (their own in-flight tracking was private before this). `meter.py` is trimmed back to just the context bar: `NOTICE_SETTING`/`build_notice`/`refresh_notice`/the far-right-padding `_paint` logic are gone, all replaced by this widget. The existing `show_index_notice` setting is renamed `show_background_status`, since it now gates all four, not only indexing.

**The phrases: `status_phrases.py`, generated once per persona, cached, from its soul.** There is no "persona creation" event anywhere in Sympose to generate these at (a persona is just a `persona.yaml`/`soul.md` someone writes by hand) — so, discussed and agreed directly with the user, generation is lazy: the first time a persona is ever used and it has no `status_phrases.md` yet, a background call (fired alongside recap/memory refresh, at launch and persona switch, unconditionally — no knob, since this is a one-time cost per persona forever after, not a recurring one like recap/memory) asks the model for 12 short phrases in that persona's voice, from its `soul.md` (or `DEFAULT_SOUL` when it has none) via `STATUS_PHRASES_INSTRUCTIONS`, and caches them to `profiles/<handle>/status_phrases.md`, one per line, plain text — the same transparency ADR 041 already chose markdown files for ("the user can open the file and fix or delete a line"). Never regenerated automatically. Never gated by cloud sharing: `soul.md` is the persona itself, already sent with every turn regardless of `cloud_share`, not the user's own data. Until a persona has its own set (still generating, or the call failed), `background_status.py` falls back to a small generic pool (`status_phrases.FALLBACK`) so there is never a gap with no phrase at all — and this fallback pool is deliberately generic, no persona voice baked in, since Samantha is the only persona that ships as a product default (`CLAUDE.md`) and her voice must not leak into what every other persona sees before its own set exists.

## Measured (2026-09-29, real model calls, scratch data only)

A scratch persona (`VAULT_PATHS` emptied, a temporary `SYMPOSE_PROFILES_DIR`), `soul.md` set to "Warm, curious, a little playful. Talks like a sharp friend who's genuinely interested, not a customer-service bot. Short sentences. Not afraid to have an opinion," `status_phrases.generate` run for real against `ollama_chat/gemma2:9b`: produced 12 phrases in character and in the requested busy-indicator shape ("Hmm, interesting...", "Ooh, this might be fun", "Could go either way, you know?", "Bingo!") — no explanation of what it was doing, no mention of Sympose or a model, matching the instructions exactly.

The `memory_rewrite` no-op fix from the same stretch (comparing a proposal to the file already on disk rather than trusting the model's own `NO_CHANGE` sentinel) was re-verified live here too, since it shares `propose`'s code path.

Not measured here: a cloud model on phrase generation; the actual felt latency difference at launch with `memory_auto_refresh` off (the fix restores an already-measured baseline, ADR 023, rather than establishing a new one).

## Consequences

- `/settings` gains `memory_auto_refresh` (off by default) and `show_background_status` (on by default, renamed from `show_index_notice`); the cloud-share screen is unaffected (status phrases are never gated by it, per the reasoning above).
- `meter.py` loses `NOTICE_SETTING`, `build_notice`, `refresh_notice`, and the far-right-padding logic in `_paint` — the ~15 tests that covered that behavior moved with it, rewritten against `background_status.py`'s actual, simpler shape (its own dedicated line needs no right-edge padding or resize handling).
- `engine.__init__` gains `refresh_status_phrases` (from `status_phrases.generate_in_background`), called unconditionally alongside the (now-gated) `refresh_memory` at launch and persona switch.
- Every reference note mentioning the old "`indexing NN%` at the right end of the line under the chat box" (`Settings.md`, `How Samantha uses your notes.md`, `Troubleshooting.md`) is updated to describe the new line's location instead; `tests/live_retrieval_cases.py` confirmed no regression from the edits.

## Amendment (2026-09-30): the reply itself is a phase too

damiro noticed the gap live: "is the status phrases not applied when the user is waiting for sams reply? I didnt see it when im waiting for her reply." Correct — the original design covered the four *background* jobs (recap, memory, phrase generation, indexing) but never the wait most turns actually spend most of their time in: the reply itself being generated. He also asked for more than a generic "she's thinking" phrase here — "real statuses like pulling notes, reading notes, searching" — since `turn.py`/`lookup.py` already know exactly what they're doing at each point of a turn.

Built: `sympose/engine/turn_status.py`, a plain per-handle `(dict, threading.Lock)` pair like `recap_refresh._RUNNING`'s own shape, holding one of three real phases — `searching`, `reading`, `asking` — for whichever handle's turn is in flight, read by `background_status.activity()` and shown as literal text (`REAL_STATUS_TEXT`), not a persona-voice phrase, since these say what is actually happening, not a vibe. `turn.run_turn` sets `asking` as the default for the whole call (cleared in a `finally`, so a raised `EngineModelError` or anything else never leaves a stale phase showing), narrowed to `searching` around `followup.ground`'s vault search (auto mode only — `ask` mode does not search before the reply, ADR 040) and back to `asking` once it returns. `lookup.converse`'s tool-calling loop (`ask` mode) sets `asking` at the top of every round and, for each tool call the model makes, `searching` for `search_notes` or `reading` for `open_note` before running it — so a multi-round `ask` turn genuinely narrates each lookup as it happens. One deliberate exception: `turn.py` clears its own phase (rather than leaving it `asking`) for the exact window it calls `recap_refresh.wait_for_refresh` — that block is really the recap job's own doing, so `activity()`'s priority order (the turn's own real phase first, then recap/memory/phrases/indexing) falls through to the recap job's own, more accurate reason for the wait instead of a misleading "asking."

Live-verified against `gemma2:9b`: a real turn on a scratch vault showed `searching` then `asking` in order, cleared to nothing once the (correctly grounded) reply returned. `ask` mode's tool-round phases (`searching`/`reading` per call) are covered by a scripted-model unit test rather than a live one, since local models available here were already established (ADR 040) not to reliably call tools. Every new phase transition was revert-checked: the fix removed and the corresponding test shown to fail, then restored. `background_status.py`'s module and `activity()` docstrings updated; `Settings.md`'s `show_background_status` entry updated (verified no retrieval regression, `tests/live_retrieval_cases.py -v` byte-identical against a baseline of the file before the edit).

**Same day, second follow-up: a long real phase now rotates in a witty line.** damiro, right after seeing the literal phrase sit still for a slow reply: "can we fill the witty when for example the reading takes too long? so that it feels a lot has been going on." Agreed default: 3 seconds. A real phase (`searching`/`reading`/`asking`) that runs past `_REAL_ROTATE_AFTER` (3s) starts alternating with a random pick from the persona's own `status_phrases`, swapping every `_REAL_ROTATE_INTERVAL` (also 3s) — the literal phrase reasserting itself on every even slot, so the line stays honest about what is actually happening at least as often as it stays lively, rather than drifting into pure vibe for a long wait. One real bug found writing the test for this: the first attempt monkeypatched `time.monotonic` directly to fake the clock, which froze it process-wide — including asyncio's own event-loop clock, which `pilot.pause()` depends on — and hung the test forever (caught, not shipped; killed and root-caused before the second attempt). Fixed by giving `background_status.py` its own private `_monotonic` reference (`from time import monotonic as _monotonic`) instead of holding the whole `time` module, so a test patches only this module's own binding and leaves the real clock untouched everywhere else. Revert-checked as usual (the rotation logic removed, the test shown to fail on the unmodified line, then restored); full suite (2255 tests) green, ruff clean.

## Not fixed (out of scope for this record)

The correctness gap found alongside the timing bug — a persona describing her memory as session-only even when `context.md`/`profile.md` content was actually sent to her — is a `SYMPOSE_RULE`-deference miss, the same class of issue already flagged and left unfixed in the checklist for grounded notes generally. It is not a timing problem and this record does not touch it.

## Alternatives rejected

- **A blocking loading bar at launch covering all "preliminaries."** The user's own first instinct. Rejected: it would reintroduce, for every launch, the wait ADR 023 deliberately removed by moving recap refresh to a background thread — trading an occasional slow first reply (the actual, narrow bug) for a guaranteed multi-second wait on the overwhelming majority of launches where nothing is wrong.
- **Sequencing `memory_refresh` behind `recap_refresh` (`wait_for_refresh`) instead of gating it off by default.** Considered as the other option when the bug was first found. Rejected as the primary fix, though not incompatible with the knob: it would reduce but not eliminate the chance of a fast first message still landing during whichever one background call is currently running, whereas dropping the automatic trigger for a job that's meant to be rare anyway removes the added contention altogether, restoring the exact baseline that was already measured acceptable.
- **A fixed, generic pool of witty phrases, no persona voice.** The user's explicit ask was persona-flavored phrasing "so the vibe is the same." Kept as the fallback only, for the gap before a persona has generated its own set.

## Amendment (2026-09-30): background jobs rotate too, and a phrase is typed out by letters

**Found live (damiro): "the witty expression doesn't really change after 3 seconds."** Reproduced with a scripted clock: a real phase (searching, reading, asking) alternated as designed, but a background job (a recap or memory refresh, indexing, phrase generation) picked one witty phrase when it started and showed it for as long as it ran, and those are the longest waits (the wait before a first message is usually a recap). Rotation had only been wired for the turn's real phases. A random pick could also land on the phrase already showing, so even a rotating line sometimes did not appear to change.

**Decision.** Every kind rotates. A background job shows a new witty phrase every `_REAL_ROTATE_INTERVAL` (3 s, as agreed for the real phases); a real phase keeps its rule (the literal phrase, then witty from 3 s, the literal one again every other slot). A witty pick never repeats the one just shown when the persona has more than one phrase.

**Typed out by letters (damiro).** A phrase appears one letter at a time, from the moment it is chosen, at `status_typing` characters per second (default 40; `0` shows it whole at once, for anyone who finds the motion tiresome). A setting and not a literal because it is a preference (ADR 032 did the same for the reply's speed), listed with the terminal's display settings in `/settings`, read on the next tick. The spinner keeps its own pace: the line is redrawn at 25 frames a second so the letters look smooth, and the spinner advances every third frame, as before. A line is only redrawn when its text changed.

**Not done.** The web chat's status text (`PHASE_TEXT`) is still fixed and does not rotate or type: it has no persona phrases yet (ADR 044, slice 3).

**Alternatives rejected.** Typing only the witty phrases: the literal text would then appear instantly beside a typed one, which reads as two systems. A fixed speed with no setting: some users do not want motion in the line, and the reveal speed already set the precedent.
