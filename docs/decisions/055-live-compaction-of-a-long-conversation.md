# 055. Live compaction of a long conversation

Status: Accepted (design talk and real-model checks, 2026-10-02). Issue #19. Related: #11 (dropping history in larger steps), #17 (the first-reply wait on a long chat). Built (2026-10-02): the engine, the terminal chat and the web chat. "As built" below records where the build differs from the first design; "Measured later" holds the cloud, several-conversation, model-switch, threshold and first-reply measurements (#125).

## Context

A conversation that outgrows the model's window loses its oldest turns. The engine drops whole turns from the oldest end when the prompt does not fit (ADR 015, `budget.fit`), a hard cap of 20 turns applies first (`session.history_as_messages`), and the header says how many were left out. The saved session file is never changed by this (ADR 023): only what is sent is trimmed. So the persona forgets how a long chat began, and the user sees only a note saying so.

Compaction replaces the oldest part of the history with a short model-written summary, so the conversation keeps its gist in much less room. Beyond keeping a long chat coherent, a shorter prompt shortens the wait for the first word, which grew to 45 to 101 s on a long chat (#17). What it builds on: the budget and the fitting loop (ADR 015), the meter (ADR 018), recaps, which are already model-written summaries kept beside the session (ADR 023), and the sharing rules for what a cloud model may receive (ADR 031).

## Decision

**What is summarised, and from what.** Like a recap (ADR 023), a compaction summary is written from the user's messages only, not the persona's replies. This was the fallback the first draft of this record named, and the first measurement below chose it: summarised from both sides, her own invented claim (a birthday she was never given) was written into the summary as the user's fact in 5 of 5 runs, even with an instruction to mark her statements as hers. What the persona herself said in the turns that are condensed is therefore not carried over: the same as today, where those turns are dropped, so compaction keeps what the user stated and decided and adds no new risk. The most recent turns stay word for word, so what she said a moment ago is still in view.

**Where it lives.** The session file stays the source of truth and keeps every turn word for word. A compaction is one extra marked line appended to the session file (`{"type": "compaction", "through": N, "text": ..., "model": ..., "timestamp": ...}`): the first `through` turns are covered, with the summary text, the model that wrote it and when. Each turn rebuilds the history from the file: the latest compaction's summary first, then the turns after the ones it covers, then the usual fitting. A resumed conversation therefore keeps its compaction. The line is plain text the user can open. A later compaction covers everything the earlier one did plus the turns since, so only the newest matters.

**What the user sees.** A line in the chat where the condensing happened ("earlier turns condensed"), and a way to read the summary. The meter (ADR 018) drops after a compaction, and the header's "older turns out of context" notice counts only turns dropped beyond it.

**When it runs.**

- **Manual:** `/compact` in the terminal and a Condense button in the web chat (it has no slash commands). It runs whenever asked, on whatever model is selected, and folds everything but the newest three turns.
- **Automatic:** a setting, `auto_compact`, **on by default for local and cloud models alike** (the same choice as recaps, ADR 023; the setting is the way out). It is read like the other display and behaviour knobs: only an explicit `false` turns it off. When a reply lands and the prompt has reached a high share of the budget (`compact_at`, 80 percent unless the user sets it), the oldest turns are condensed in the background, so the user is never left waiting for it, down to a lower share (`compact_to`, 40 percent, always below the first), keeping the most recent turns word for word. Condensing in one larger step, not one turn at a time, keeps the start of the prompt unchanged for many turns so Ollama can keep reusing its work; this is the stepped drop of #11, which this closes if the measurement agrees.
- Both channels (terminal and web chat) use the same engine function; neither carries its own logic.

**Who writes it, and what leaves the machine.** The model that is running the conversation writes the summary (or, for a persona with its own model, that model). A summary restates text that model already receives as history, in less room, so it sends nothing that was not already being sent. The one new cost is that on a cloud model each compaction is one extra paid call, which is what `auto_compact` controls. A summary written by one model and later sent to another (after a model switch) is conversation content like the turns it replaced and follows the same rule as them. If review finds a case where it should be gated by `/share`, a category is added then, not guessed now.

**If it fails.** A failed call, an empty summary or one longer than the turns it replaces writes nothing, and the engine falls back to what it does today (drop the oldest turns and say so). The session file is never at risk. A failure never blocks a reply.

**The 20-turn cap.** Turns beyond the cap are folded into a compaction instead of silently hidden, so the cap stops being a quiet forgetting.

**Order of what is sacrificed when space runs out** is ADR 015's, unchanged: recaps, then decisions, then the oldest kept turns, then grounding passages. The notes are not in that list: they are fixed for every attempt of the fitting loop, like the vault map and the persona's own memory, since they are all that is left of the turns they replace and cannot be more than about 150 words (this replaced the first design, which had them go last from the history side).

## As built

- `engine/session_compaction.py` reads, validates and appends the record (a damaged or hand-edited one is skipped, the last good one is in force, `through` is never more than the turns there are); `engine/compaction.py` holds the policy and the model call; `engine/compaction_text.py` the request and the label the notes carry in the system prompt (placed after the recaps, closest to the history). `session.history_as_messages` leaves out the turns the notes stand for; `turn.run_turn` puts the notes in the prompt, reports `condensed` on the result and, after a saved reply, starts the automatic run on a background thread (`background_job.Runner`, one per conversation, so `/compact` while one runs is told it is busy).
- **The notes are rolling.** A second compaction is written from the notes so far and the user's messages that came after them, not from the whole conversation again, so each call stays small however long the chat gets. (Three in a row were measured, below.)
- **How much is folded** when the automatic run starts: the fewest of the oldest turns that bring the conversation down to `compact_to`, never the newest three, and always the turns beyond the 20-turn history cap. What one request cannot hold within the window is left for the next compaction.
- **A run that wrote nothing is not repeated at once:** after an automatic attempt that failed or would not save room, the next one waits for five more turns, so a model that is down, or turns too short to be worth notes, cost no call (on a cloud model, a paid one) every turn.
- **Settings** (shared by `/settings` and the web settings page through `engine/settings_registry.py`): `auto_compact` (a toggle, on), `compact_at` and `compact_to` (whole percents, 10 to 95; `compact_to` is always below `compact_at`, so a bad pair is not accepted). Tests start with `auto_compact` off (`tests/conftest.py`) so no unrelated test starts a background model call; the shipped default is `compaction.DEFAULT_ON`.
- **Terminal:** `/compact` (off the interface thread, on a pool of its own) prints the size before and after and the notes, and refreshes the meter; with nothing more to fold it shows the notes in force. The reply header says `N earlier turns condensed` once, on the reply that first used the notes or when they grew, behind `show_trim_notice`.
- **Web chat:** `POST /api/chat/compact` (always answers with the notes in force), the notes and what they stand for on a conversation's page (`compaction`), and `condensed` on a turn's answer. A Condense button beside New conversation; the notes show as a line of their own, and when a conversation is resumed they show where they take over from the turns above. The meter's figure is asked for again after condensing (it kept the longer conversation's figure until the real browser showed it).
- The meter's estimate after a model switch (`engine/context_estimate.py`) counts the notes too.

## Measured so far (`gemma2:9b`, 5 runs each, an invented 11-turn conversation of 524 tokens with planted facts and a planted false claim by the persona; a minimal system prompt, not the engine's full prompt)

- **Both sides, asked to mark her statements as hers:** user facts survived 15/15 and her suggestion 5/5, but the false birthday was written into the summary as a fact 5/5 and then repeated as the answer 5/5. Rejected.
- **The user's messages only:** facts 15/15; the false claim never appeared (0/5) and she did not invent a date when asked (5/5); her earlier suggestion is not remembered (0/5), by design. The summary was about 108 tokens for 524, and took 12 to 49 s (the 49 s one included loading the model).
- **User's messages and her replies summarised in two separate calls, labelled by code:** worse. The notes on her replies covered only the first reply, the birthday answer was fine in 3 of 5 only because she answered with a placeholder or an invented date, and it took about 51 s for 297 tokens. Rejected.
- **Caveat:** the probe used a minimal prompt in which she sometimes said she keeps no memory of earlier conversations; how the engine's real prompt, which tells her what she has, changes that is checked through `run_turn` below.

- **Through the real engine (`run_turn`, Samantha's real soul and rules; 2 runs per question; one invented conversation):** with no compaction the persona repeated her own earlier false birthday 2 of 2 times, because her reply was still in the history; with the notes (either placement below) she never did (2 of 2 each) and said she had not been told. The facts the user stated were kept: 6 of 8 with notes against 7 of 8 without, and of the four misses two were the checker being too strict about wording and two were the test vault's own "Budget" note being retrieved instead (it also happened once without compaction). She did not say she has no memory of the earlier conversation. The notes were tried in the system prompt (A) and as the first user/assistant pair of the history (B): no difference at this sample size, so **A is the decision**: the notes are a block in the system prompt, after the recaps and before the grounding, and need no invented assistant turn. They are the last thing sacrificed from the history side when space runs out.
- **The first-reply wait on a long chat** (20 turns, 4,794 tokens against a prompt budget of 6,144; the model unloaded before each call; 2 runs): full history 96.5 s and 101.3 s; condensed (notes plus the last 3 turns, 1,924 tokens) 43.9 s and 41.9 s. The wait follows the prompt size at about 50 tokens a second on this machine.
- **Successive turns once the window is full** (8 turns, one run each, filler text, model loaded): dropping one turn out at a time, as today, cost 100 to 112 s on every turn (mean 106 s), because the start of the prompt changes each turn and Ollama redoes its work. One stepped drop (to 40 percent when 85 percent was reached) cost 6 s on the two turns before the drop, 50 s on the turn that dropped, then about 30 s on each of the next five (mean 27 s). The five at about 30 s were slower than the 6 s before the drop and this was not explained: the prompt start was unchanged there, so more reuse was expected. Treat the mean as a direction, not a figure. Only that one pair of thresholds was tried, so 85 and 40 percent are starting points that this measurement did not tune.
- **A limit found on the way:** the engine gives every model call 120 s (`_REQUEST_TIMEOUT_SECONDS`, `engine/model.py`). On the measured machine a cold start with a prompt of about 4,900 tokens takes about 100 s, so a longer chat reaches the limit and the reply fails with "couldn't reach the model" instead of being slow. Compaction makes this rarer; the limit itself (a fixed number against a wait that grows with the prompt) is separate work and is not changed here.

- **Three compactions in a row** (14, then 22, then 28 turns, through `compaction.compact_now` with the real engine; one invented conversation): the notes kept the early facts through every roll (the launch date, the database, the budget, the logo's maker, and the later hosting, domain and a friend's bug), 609 tokens became 112, then 470 became 179, then 410 became 224, and no number appeared in the notes that no message of the user had. Asked afterwards, the persona answered the facts from the notes 3 of 4, 5 of 7 and 6 of 7 times (the later ones cannot be known earlier); the misses were two kinds: the test vault's own notes ("Budget", "Atlas") answering a question that was about the conversation, which also happens with no compaction, and the launch date, which she gave as "the first week of November" from the vault's Atlas note 3 of 3 times in that run and 1 of 5 times in a repeat that isolated the cause (the label in front of the notes made no difference: 4 of 5 with the new label and with the earlier one). So a vault note about the same subject can still win over the notes of the conversation; this is the grounding behaviour that exists without compaction, not something compaction adds.
- **The web chat in a real headless Chrome** (a scratch vault, profile and settings, a seeded conversation of 14 turns, the real model): the Condense button disables and says it is working, 11 turns became notes (609 to 111 tokens), the notes show in the transcript, a reply afterwards does not announce them again, and after a reload the notes show where they take over and the next reply does not announce them either. It found a bug the unit tests had missed: the meter stayed at ~31% after condensing a resumed conversation (its estimate was not asked for again); it reads ~25% now.

## Measured later (2026-10-03, #125)

All on invented conversations and filler text on scratch data, through the real engine (`compaction.compact_now`, `run_turn`); the probes are kept outside the repository. The machine is the same as above (`gemma2:9b`, a window of 8192 and a prompt budget of 6144).

- **Several conversations (point 2).** Four invented 14-turn conversations (a website plan, a trip, an exam plan, a script that crashes), each with a fact the user gave, a suggestion the persona made and a false claim by the persona (a saved birthday, a reservation name, a reminder time, a run time). 3 runs each on `gemma2:9b`: notes of 107 to 182 tokens for 534 to 609, 17 to 33 s to write; the user's facts were answered 35 of 36 times (the miss: a data volume of 2 GB a night, which she did not recall), and the false claims never came back (12 of 12). **Her own earlier suggestions are not kept, as designed, and she sometimes makes one up:** asked "which web server did you suggest?" (it was Caddy) she said Nginx 3 of 3 times. A user's own words survive; hers do not, and a model that fills the gap with a guess is the cost of the choice made above. It did not happen with the cloud model (below), which said it had no record. Whether the persona's prompt should tell her more plainly that her own replies are not in the notes was tried afterwards (2026-10-03, `gemma2:9b`, the four conversations, 3 runs of the question about what she had suggested, 12 answers) and **not adopted**: with the notes' label extended by "If asked what you said, suggested or promised earlier in this conversation, say you no longer have it; do not guess", she still answered Nginx for Caddy 3 of 3 (2 of 3 without the line) and made up or guessed an answer in 6 of 12 answers against 4 of 12 without it; a small model does not follow the instruction. The structural answer is ADR 056: with `past_chats` on, her own earlier replies can be found again, marked as hers.
- **A cloud model (point 1).** `gemini-3.8-flash`, the same four conversations, 3 runs each: notes of 136 to 145 tokens for the same 534 to 609, in 3.5 to 15 s; facts 36 of 36, false claims never repeated (12 of 12). Each compaction is one extra call of about 700 tokens in and 140 out, written once and then rolled (the next one reads the notes and only the newer messages). A price is not given: it depends on the provider and changes. Two things to know. The earlier Gemini models (`2.5-flash`, `2.0-flash`) answer 404 now, so a user whose persona is set to one gets the "couldn't reach the model" message and no notes; and in later runs 4 of 8 notes calls took 78 to 156 s and one stalled past 300 s in a first attempt, never reproduced. Because the automatic kind runs in the background, a slow call delays the notes, not a reply.
- **Notes written by one model, read by another (point 4).** Notes by `gemma2:9b`, questions answered by Gemini: facts 23 of 24, false claims 8 of 8. Notes by Gemini, questions answered by `gemma2:9b`: facts 23 of 24, false claims 8 of 8. The misses were one forgotten number in the first case and a mix-up of the last turn in the second. Notes written by either carry across; switching models after condensing is safe.
- **First reply after condensing, end to end (point 5).** A chat seeded to 80 percent of the budget, one real turn (which starts the compaction when it is on), then the model unloaded before each timed turn, 2 runs: **with automatic compaction on, 59.8 s and 60.8 s to the first word at about 3,100 tokens; with it off, 128.7 s and 133.0 s at about 6,000 tokens** (the second of those was over the budget, so a turn was dropped). About half, which follows the prompt size as measured before.
- **Ten quick turns, the next message sent as soon as the reply lands (point 3, the pair of thresholds and the summary competing for the GPU).** Seeded at 9 turns (about 60 percent), then 10 turns of long messages; turn 1 includes loading the model (84 to 119 s in every run). Mean first word over turns 2 to 10: **no compaction 65 s** (a 120 to 130 s turn every time a turn was dropped, 3 of 9 turns), **70 and 30: 33 s, 80 and 40: 33 s, 90 and 50: 31 s**. The compaction that follows a reply ran while the next message was already waiting, and that next turn was not slower for it (26 to 32 s); the turn after it paid for the prompt's start having changed (51 to 63 s once, then 44 to 50 s), and every turn from then on was 20 to 30 s. **The three pairs did not differ**: the seeded chat was already at 93 percent after the first turn, so all three fired on the same turn and landed at 47 to 55 percent; a real difference would be how often each fires over a long chat, which ten turns cannot show. The defaults (80 and 40) stay; 70 and 30 would condense a chat that is still at 70 percent again at turn 11, and 90 and 50 would run closer to the edge of the window, and neither was shown to be better. Dropped as a tuning exercise, with that reason.
- **The 120 s call limit** is answered by ADR 059 (the wait grows with the prompt and `model_timeout` sets it).

## Update: `history_tokens`, an optional cap on the earlier turns (2026-10-02, with #125)

**Context.** Compaction holds a conversation between `compact_at` and `compact_to` of the prompt budget, so the earlier turns can still take most of the window. The wait for a reply grows with the prompt (ADR 059): about 97 s cold at 4.8k tokens on `gemma2:9b`. A user on a slow machine, or paying per token, may want a short history whatever the window allows, and a user who does not want notes at all has no way to say so.

**Decision.** `history_tokens` (whole tokens, 500 or more; empty or unusable means no cap, which is today's behaviour) is the most the earlier turns of the conversation may take in a prompt, word for word. Before the prompt is fitted, the oldest turns are dropped until what is left is within the cap; the newest turn always stays, even when it is over. The turns dropped are counted with the ones the window's own fitting drops, so the "older turns out of context" notice (`show_trim_notice`) says so. Notes already written (the compaction's record) are not part of the cap: they are the short stand-in for the turns they replace, and a user who wants none sets `auto_compact` off. The cap is in the shared settings registry, Context group, in both channels.

**Consequences.** A capped conversation drops turns instead of condensing them: with a low cap the prompt never nears `compact_at`, so the automatic compaction does not start and the early part is forgotten, which is what a cap asks for and what #19 was written to avoid when a user has not asked. `/compact` still works and writes notes the cap does not touch. The default is no cap, so nothing changes for anyone who does not set it.

**Alternatives rejected.** A cap as a share of the window: that is `compact_at`, which keeps the gist as notes. Making the cap the default: it forgets silently.

## Alternatives rejected

- **Summarise both sides, her statements marked as hers.** Measured and rejected: it recorded her invented claim as the user's fact 5 of 5 times. A separate call for her side, labelled by code, was worse.
- **Only manual.** A long chat would still forget silently until the user thought to ask.
- **Rewrite the session file with the summary in place of the turns.** The log is the source of truth and the record of what was actually said (ADR 023); a wrong summary must be replaceable from it.
- **Condense one turn at a time.** It changes the start of the prompt every turn, so Ollama redoes its work each time, which is the wait this is meant to shorten.
- **Off by default on cloud models.** It would keep the paid call from ever being unasked, but it leaves cloud users on the silent forgetting; the setting is the way out instead.
