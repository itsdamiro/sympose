# 069 — Highlights and comments on a note: kept out of the vault, sent with the next message, read by the persona

> **Summary.** Highlights and comments on a note are kept in the persona's own data folder, never in the vault or the note, and travel with the next message so the persona reads them. Quoting the passage back into chat was slow and lost where it was in the note. It adds a store, a small API, a new `/share` category and one more prompt block.

> **Status: Accepted, built (2026-10-05); the table-cell amendments are in the sections below.** Proposed 2026-10-04. Part of #21 (a persona that acts on the vault) and the companion of the ADR 042 amendment of the same date: tracked changes are what the persona writes into a note, and this is what the user marks in it for her to read. Turn-based throughout.

## Context

The user wants to discuss a note with the persona by pointing at it: highlight a passage, write a comment on the highlight, and have the persona read both when they talk. Chat alone makes the user quote the passage back, which is slow and loses where in the note it was. The editor already shows the note; what is missing is a way to mark it that the persona can read.

Constraints that shape the design, from the project's own rules:

- Plain text stays canonical: the note's Markdown is the user's, shared with other tools, and is not the place for annotation syntax.
- Files the user did not create must not appear in the vault they browse: a visible sidecar would confuse (ADR 042 amendment, `.trash` being the one deliberate, user-facing exception).
- Anything derived from the vault that a cloud model would receive must be known to and approved by the user, controlled by a setting (ADR 031).
- Cheap by default: no extra model round trip for a feature that can ride a message the user was sending anyway.
- Web app only: the terminal is not expected to create or edit notes.

## Decision

**What an annotation is.** A highlight is a range of a note; a comment is text attached to a highlight, and a persona reply is a comment of the persona's under it. Each has an id, an author (user or persona), a state (open or resolved) and a time.

**Where it lives.** In the persona's own data folder (`profiles/<handle>/`, beside sessions and memory), in a file keyed by the note's vault-relative path. Never in the vault, never in the note's Markdown, never a visible sidecar. Deleting or moving a note in Sympose carries its annotations with it, as the pinned list and the trash index already follow a note.

**How a highlight finds its passage again.** By the quoted text plus a little text before and after it, not by an offset: an offset breaks on the first edit above it. The editor re-finds the passage when the note opens and maps it through the user's edits while it is open. When the quoted text is no longer in the note, the highlight is shown as detached, never silently moved to a guess, and the user can re-attach or resolve it.

**How the editor shows it.** The highlighted passage is tinted, and a marker in the margin, where a line number would otherwise be, shows that a highlight or comment is there; selecting it opens the comment thread over the highlight. Each persona comment carries its own Accept and Decline (Accept keeps it, Decline dismisses it). Drawing this needs extensions on the editor view; ADR 042's amendment names the spike that checks whether that works through stylo's `getView()` or waits for a stylo request.

**How the persona reads it.** Annotations travel with the user's next chat message as context. When the user sends a message, the open annotations on the note that is open in the editor go with it, each with its quoted passage and comment, labelled new since the last message or earlier. The persona answers in chat, may reply under a comment, and may propose a tracked change at the highlight. Either side resolving a comment stops it travelling. Because old open comments travel too, she does not forget what the user flagged two messages ago, and a cap on how many go in one message keeps a long list from inflating every turn (the number is set from measurement, not guessed here).

**Cloud models.** Annotations are vault-derived (the passage and the user's own words about it), so they are a new category in `cloud_share` (ADR 031), named `annotations`, off until the user approves it; a local model receives them freely. With the category withheld the persona is told they were not sent and how to allow them, the same way the other categories do.

## Built (2026-10-04, #21 slice 3b): the editor side

The user selects words and presses the toolbar's Comment button (greyed while nothing is selected), and a box opens on the selection; clicking a highlighted passage opens its thread on the passage. In a thread the user answers, resolves (the answers go with it) or deletes (after a confirmation that says the replies go too). Details settled in the build:

- **The editor sends the text around the selection.** It has the text as the user sees it, which can be ahead of the file and is the note's body only (the frontmatter is not in it), so offsets would not match the file. The request carries the quoted words and the text just before and after them, and the backend keeps that as the anchor without looking for the words in the file; with only half the context it falls back to finding the passage in the note.
- **A reply is about its comment's passage.** `reply_to` names the comment and the passage and context are copied from it; a reply to a reply goes under the comment it is in. Resolving or reopening a comment does the same to the replies under it.
- **One highlight per comment.** Replies share their comment's passage, so only the comment is drawn and counted for the margin dot.
- **Resolved comments are not drawn.** There is no screen yet to see or reopen a resolved one.
- **The persona's name** in a thread is the active persona's display name.
- **Closing on a note change.** A box opened on one note closes when another opens, so a comment written for one is never saved onto the other.
- **The toolbar reserves room for the panel's floating controls** (frontmatter, read and edit, the note menu), which were drawn over the end of the toolbar row and hid its last buttons, Save among them, at the default panel width; the buttons now wrap onto a second row instead.

## Consequences

- A new store in the persona's data folder and a small API for the editor to read and write annotations; the chat request carries the open note's path so the engine can attach its open annotations.
- A new `/share` category and one more block in the prompt, with the same gating, withheld-notice and test pattern as `connections`.
- Passages shown to a model are text the user chose to highlight; the engine treats a comment as the user's own words and the quoted passage as untrusted vault text, as every passage already is.
- Not built for the terminal.

## Open questions

- The cap on annotations per message, and whether older resolved ones are ever summarized; to be set from a measurement on a small and a cloud model.
- Whether a highlight may span several paragraphs or is limited to one block; the first version may limit it to keep re-finding reliable.
- Whether a highlight with no comment still travels (it marks "look at this") or only commented ones do.
- How a note's annotations are cleaned up when a note is permanently deleted from the bin.

## Amendment (2026-10-05): which comments are new since her last reply

ADR 072 said the comments travel "labelled new since the last message or earlier". Built so: each open comment is marked **new** when the comment or any answer in its thread is newer than the previous turn of this conversation (the `timestamp` the session already records for that turn), and **earlier** otherwise; the block reads `On “passage” (new since your last reply):` or `(from before your last reply):`. Times are compared as times (the session's carry fractions of a second, a comment's do not). A comment of hers made during the last turn is earlier. **The first message of a conversation carries no label at all**, since there is nothing to contrast with. Nothing new is stored: the comments' own times and the session's turn times are enough, and a conversation that was compacted or resumed behaves the same because the turns' timestamps remain.

**Measured (2026-10-05, invented notes, four runs each, a throwaway script):** asked "What have I added since your last reply?" with one new and one earlier comment, `gemma2:9b` named the new one 2 of 4 with the labels against 1 of 4 without, and presented the earlier one as new 0 of 4 against 1 of 4; Gemini Flash named it 4 of 4 against 2 of 4, and never presented the earlier one as new either way. So the labels help and cost nothing measured.

## Amendment (2026-10-05): comments inside table cells (stylo 0.20.0)

A decoration cannot reach a table cell, so the highlight of a comment on words inside a table was not drawn (the comment itself saved and attached). Stylo 0.20.0 takes `inPlace.cellMarks(state)` and draws the marks it returns on the characters of a cell, and gives a menu item `run(view, { rect })`. Built: `cellMarks` (`lib/review-extensions.ts`) returns one mark per open comment (the user's amber, hers the brand blue, with `data-comment-id`) and one per edit she has applied, and gives the cell the author's dot in its corner; the Comment item opens its box beside the rectangle stylo gives, where it used to open under the table. The marks use their own class (`sy-hl-persona`), not `sy-by-*`, which also carries the margin-dot rule for plain text and put a stray dot at the cell's edge for every highlighted word. A click on a marked word in a cell did not arrive on 0.20.0 (the press rebuilt the cell as it took focus, so the browser sent no `click`); stylo 0.20.1 keeps the pressed word until after the release, so the thread now opens on a plain click in and out of cells, and the mouseup workaround was removed (checked in real Chrome: a real click on a marked word opens the thread, the cell still goes into editing, and the words carry `data-stylo-cell-mark`). Not covered: a change she proposed inside a table (the struck words, the new ones and their buttons are widgets, not marks); Accept all on the toolbar still applies it.

## Amendment (2026-10-05): Accept and Decline on her comments

**Decided with the user.** A comment of hers can be accepted or declined, one comment at a time, in its thread. **Accept** means the user agrees with her point: the comment is resolved with the verdict `accepted`. **Decline** means they do not: the user must have replied in the thread first, saying why, and then the comment is resolved with the verdict `declined`; the Decline button is greyed until they have, and the server refuses a decline without a reply from the user (`400`, "Reply first, saying why you disagree."). Only a root comment whose author is the persona can be given a verdict (the user's own comments are resolved or deleted as before, and `400` otherwise); a verdict resolves the comment and its answers together, and reopening the comment clears it. The verdict and the time it was given are kept on the comment (`verdict`, `decided`).

**She is told.** What the user decided is carried to her once, in the next message after the decision: the comments she made that were accepted or declined since the previous turn of the conversation (the same "since" as the new/earlier labels above), as `On “passage”: accepted.` or `On “passage”: declined, the user wrote: <their last reply>.`, newest within a small cap. Nothing is sent on the first message of a conversation, nothing when the model may not have comments (the `annotations` category, ADR 031), and a decision is not repeated after that turn. Resolved comments are otherwise not sent.

**Built and checked (2026-10-05).** In a real browser: Accept is offered on her comment, Decline is greyed with a hint until the user has replied, then declines; both resolve the comment and its highlight goes. Real-model check on invented notes (four runs each, `gemma2:9b` and Gemini Flash): asked what she would still flag after the user declined her point about moving the carrots, neither model raised it again, with the decision line or without it (0 of 4 in all four cases), so the scenario did not tell the two apart: the line is not shown to help or to harm. Not built: a way to see a resolved comment's verdict in the thread afterwards.

## Amendment (2026-10-05): her changes inside table cells (stylo 0.21.0)

The previous amendment left one hole: a change she proposed inside a table was stored but drawn nowhere (a widget decoration is dropped inside a table, and the struck words were not marked in cells), so the Drafts list counted it while the note showed nothing, and the only way to apply it was Accept all on the toolbar, which applies what the user has not been shown. That broke the rule that the file changes only when the user has reviewed and accepted. Checked in real Chrome on stylo 0.20.1 (a three-column table, two seeded proposals): the one in the paragraph was drawn with its buttons, the one in a cell left no trace on the page.

Stylo 0.21.0 takes `inPlace.cellWidgets(state)`: elements in document positions, drawn inside the cell after the characters that end there, kept out of the cell's text, and clickable without the cell taking focus. Decided:

- **A change inside one cell is drawn like any other.** The struck words are a `cellMarks` entry (class `sy-change-del`), the replacement and the Accept and Decline buttons are a `cellWidgets` entry at the end of the quoted words, and the same goes for the Undo element of an edit applied in `accept` mode. Positions are worked out from the editor state on every call; the key covers the proposal id, the replacement and her note. Accept and Decline stay the host's own transaction on the document text.
- **While a cell is being edited its buttons are hidden** (Stylo shows a focused cell as raw text); they return when it loses focus. Accept all and the Drafts list are unaffected.
- **A change that does not sit inside one cell is refused when she proposes it**, with a message saying why, which comes back to her as the tool's answer (the same path as a passage not found): the quoted words touch a table and run over a cell border (`|`) or a line, or the replacement would put a `|` or a line break into a cell. Stylo ignores a position that is not inside one cell's content, so such a change could not be drawn, and an undrawn change is the hole above. The cost is that she cannot add or remove a row or a column, or rewrite a whole table, through a tracked change; she can still say what she would change in a comment. A comment over several cells is not touched by this (comments are drawn as marks).
- **Where the table is.** Found in the note's text by its Markdown shape (a header row, a delimiter row of dashes, the rows below it until a blank line), skipping fenced code. Not found when it is not one of those shapes, so a line that merely contains a `|` is not a table and her change on it is left alone.

**Built and checked (2026-10-05, stylo 0.21.0).** `table_spans.py` finds tables and refuses what cannot sit in one cell (29 tests, every mutant caught); `cellMarks` strikes a pending change and `cellWidgets` draws its replacement with Accept and Decline, and an applied edit's Undo (the panel hands both to stylo; the editor tests and the panel test caught every mutant tried). In real Chrome on a scratch vault with the "Table editing" setting on **cells**: the struck words and the buttons are in the cell, a click on Accept replaces only those words in the editor, and the file on disk is untouched until a save. Not seen: the buttons hiding while a cell is focused (a programmatic caret did not focus a cell; stylo's own Chrome spec covers it).

**Reviewed and hardened (2026-10-06).** A `/code-review` and a check of my own found that the table finder missed a table in a note with Windows line endings, in a blockquote, under a list item or after a list marker, was thrown off by a line that only looks like a fence, and let through a replacement ending in a backslash (which would escape the pipe after it). All fixed with tests (the finder reads a line without its `\r` and its blockquote or indent margin, tracks a fence by its own character and length, and refuses a trailing backslash). **Known and left:** an indented code block (four spaces, not under a list) that holds lines shaped like a table is read as one, so a change across its lines is refused with the table message; a proposal stored before this check is not re-checked, and the editor's text can differ from the file the check ran against, so an undrawn change can still reach Drafts in those two cases, where Accept all would apply it.

**Found: the default setting does not draw them.** With "Table editing" on **source** (Sympose's default), a table not being edited is a static rendering that stylo does not repaint, so neither a change's buttons nor, as the same run showed, a comment's highlight appears in a cell (stylo only repaints cell marks and widgets in `cells` mode). With the caret inside the table it shows as raw rows and the change is drawn there like any text. So in the default setting a change inside a table is shown only once the user clicks into the table, and the Drafts count says it exists. Not settled: whether stylo should draw marks and widgets on the static table too, whether Sympose should open such a table raw when it holds something pending, or whether the default should be `cells`.

**Resolved by stylo 0.22.0 (2026-10-05).** Stylo drew marks and widgets on the static table too, and a click on a marked word or a host button there no longer reveals the table's source. Checked again in real Chrome with "Table editing" on **source** (the default): the struck words, the replacement with its buttons and a comment's highlight are in the cell with the caret outside the table; a click on Accept replaces only those words, the table stays rendered, and the file is untouched until a save; arrowing down onto the table shows its raw rows with the change drawn on those lines, and arrowing back out brings the rendered table back with the widget, at no point both or neither. Then with real mouse clicks on stylo 0.22.0, in `source` and in `cells`: a click on a commented word opens its thread and leaves the table rendered; Accept replaces only the cell's words, Decline leaves the text alone and the server forgets the change, the file is untouched either way; in `cells`, focusing the cell that holds a change hides its buttons (the struck words stay) and they return when focus leaves; typing in another cell, which re-pads the whole column, leaves the widget attached right after its words. Sympose's own read-only (the toolbar's read toggle) is stylo's `preview` view, not the `readOnly` prop 0.22.0 also covers: it has no editor, so none of her changes or comments are drawn in it, in a table or out of one (as before). No change to the default or to Sympose's code was needed.

## Alternatives rejected

- **A sidecar file in the vault** (`Note.md.comments` or a hidden index). Rejected: visible to the user and to sync tools, which is confusing, and it ties Sympose's own state to files the user did not create.
- **Annotations as syntax inside the note** (`==highlight==`, comment markers). Rejected: it changes the user's Markdown and breaks round-trip fidelity with other tools.
- **Anchoring by line number or character offset.** Rejected: the first edit above the passage moves it.
- **Sending only the annotations added since the last message.** Rejected as the default: the persona forgets earlier open comments; the open ones all travel, labelled new or earlier, under a cap.
- **Decline deletes the comment, and Accept only resolves (2026-10-05).** Rejected by the user: a decision should leave a record and teach her, and a deleted comment cannot be looked at again.
- **Decline without a reason.** Rejected by the user: the reason is the point of declining, and it is what she is told.
- **Let a change across cells through and leave it undrawn (2026-10-05).** Rejected: it brings back the invisible change. The user would see a count in Drafts and nothing in the note.
- **Draw a dot beside the whole table when a cell holds a pending change.** Rejected: it says a change exists, not where, and the only way to act on it is still Accept all.
- **Reaching into the cells' DOM from Sympose to draw the buttons.** Rejected for the reason the stylo requests were written: it breaks on every repaint and can write the host's labels into the user's Markdown.

## Amendment (2026-10-06): comments on the same words are one thread box, and her comment goes under theirs

A user asked the persona to delete a table; she could not (a change across cells is refused, below), so she left a comment on the same words the user's own comment was on, and the user could not find it: two highlights on one range are drawn on top of each other, and a click reaches only one thread.

- **Her comment on words that already have an open comment of the user's is an answer under it** (`note_changes.comment_on`, used by her `comment_on` tool and marker), so the two read as one thread. A resolved comment does not count; a comment on other words stays its own.
- **Comments on exactly the same words are one highlight** that carries every thread's id (`data-comment-ids`), in the note and in a table cell; a click opens the box with a thread for each, the clicked one first, each with its own reply, resolve and delete. This also covers two comments the user made on one passage.
- **The note is the truth about its comments, and the clean-up is silent.** A user who had cleared every comment they could see still saw "1" in the Drafts section: a comment whose words had been rewritten (an edit of hers accepted, the passage changed) is not drawn and not sent, so it was counted and could not be cleared. Now `note_changes.prune`, run whenever a note's changes or the Drafts list are read, deletes with its answers (a) a comment whose words are not in the note, if the note was written after the comment (a comment on words only in the editor is newer than the file and is not judged; two seconds of margin for the whole-second times), and (b) a comment the user resolved. A note left with nothing keeps no file. A persona's comment the user accepted or declined is kept until it has been told to her (ADR 069 above), then follows rule (b) only if a later change makes it so. The user is shown nothing: no notice, no list, no explanation; a comment they cannot see is simply not there, and not counted. (Two earlier tries were rejected by the user: a strip in the note listing such comments, as one more place for comments; and only not counting them while keeping them stored.) Resolve and Delete in the comment box therefore both end with the comment gone.
- **Her change answers the comment it is on, and accepting it settles the comment (2026-10-06).** A persona that acts on a user's comment ("make this bold") proposed the change but left the comment unanswered. Now her one-line explanation of a change is added as an answer under each open comment of the user's on the same words (`note_changes.propose_edit`), and when the user accepts the change the comments on its words are deleted with their answers (`settle_comments`, the `accepted` flag of `POST /api/vault/changes/resolve`); declining keeps them, so she can try again. On words with both a comment and a waiting change of hers only the change is drawn (the comment's highlight yields; it opens on a click and keeps its margin dot), and the change's Accept and Decline sit in a small tab above the words, with their words drawn by the style so they are not part of the note's text.
- **The Drafts count is the number of different marks on the note (2026-10-06).** One number ("4 to review"), not changes and comments apart: a change waiting, a new note proposed, or an open comment on words still in the note; a comment on the words of a waiting change is the same item as the change. A change or comment not marked on the note (its words gone) is not counted, and one that is gone from a note written since is deleted with the same silent clean-up.

## Amendment (2026-10-07): declining her comment needs no reply

**Decided with the user, replacing the rule of 2026-10-05 above and the rejected "Decline without a reason".** Declining one of her comments needs nothing from the user: the Decline button is always offered and the server no longer refuses a decline without a reply (the `400` "Reply first, saying why you disagree." and the hint above the row are gone). A reason is the user's own to give: if they replied in the thread before declining, she is told it as before (`declined, the user wrote: <their last reply>.`); with no reply she is told `declined.` only. Her prompt already handled both, so nothing else changes. The reason: a reason is useful to her but must not be forced; forcing it made a quick "no" a chore.

**Her decided comments are removed once she has been told (decided with the user, 2026-10-07, one highlighted item at a time).** A comment of hers that the user accepted or declined was kept so the next message could tell her; after that it stayed in her folder for good, unseen. Now each one is deleted, with its own replies, by its own id, after the turn that carried it to her has been recorded: `open_comments.gather` returns the ids to settle (`Found.settle`: the ones told in this prompt, and any decided before her last reply, which can never be told since a decision is told once, in the next message), `Edit.settle` carries them, and `turn.run_turn` deletes them right after the stop point (`turn_cancel.commit`), so a failed or stopped turn removes nothing and she is told next time. Nothing else is touched: not an open comment, not another comment on the same words (they share a highlight but are separate items), and not a decision made while the reply was being written. Nothing is removed on the first message of a conversation (no earlier reply, so nothing could have been told) or when the model may not be sent comments (a cloud model before `annotations` is approved: she was not told, so it waits).

## Amendment (2026-10-07): a row or a column is added or removed by replacing the whole table

**Decided with the user, replacing the "stays a limitation" paragraph this section first had.** A persona can add or remove a table row or column, with no new editor feature and no new tool. The change is the whole table: she quotes it from its first row to its last and gives the whole new table, and says in her reply what she changed. The user sees the table's source, the old rows struck and the new ones beside them, and **Accept, Decline and the paperclip as for any change; in `accept` mode the same change is applied at once with the Undo.** The detail (one row, one cell) is in her reply, not in the drawing, and there is no accepting or declining a row on its own: it is the whole table or nothing.

- **The rule** (`table_spans.problem`): a change that covers exactly one table (its first row's text to its last row's end) is allowed when the replacement is **one plain table**, line for line (a header row, a delimiter row of dashes, the rows below), **with the same number of cells in every row** and nothing before, after or between. So the table cannot be left broken, and a refused change says why and tells her to comment instead. Not allowed: a table in a blockquote or under a list item (its margin would be lost), a note with Windows line endings, quoting part of a table across rows, and removing the table. Inside one cell nothing changes.
- **Her prompt** (tool-calling models only, as before, since each extra line cost `gemma2:9b` edits): the table rule now says to quote the whole table exactly and give the whole new table with the same cells in every row, to say what she changed, and still not to propose any other change across cells or rows or the table's removal.
- **In the editor** (`review-extensions.ts`): such a change is told by its shape (`isTableChange`: its words and replacement both run over several lines of pipes). In a rendered table the old cells are struck as before and **the buttons are drawn at the end of the last cell** (a position after the closing pipe is not in a cell and was dropped); only the buttons, not a copy of the new rows. **The source is revealed:** when a note with such a change opens, or one arrives, the caret is put at the start of the table once for each change (`markdown-panel.tsx`), which makes the editor show the table as source, with the new rows drawn, so a change is never offered that cannot be read. Not in `accept` mode, where it is applied and drawn as applied with the Undo (the Undo is placed in the last cell the same way).
- **Seen in real Chrome (2026-10-07, scratch vault, `gemma2:9b` not involved: the change was stored through the normal path):** the source is shown on open, old rows struck and new ones green with the buttons; with the caret moved out, the rendered table shows the struck old cells and the buttons; Accept then Save writes the new table to the file (the editor aligns the columns, as it does for any table); Decline leaves the file as it was; in `accept` mode the table is applied with a green mark and the Undo (shown when the changed words are hovered) restores the old rows. Two adjacent changes in the source draw their tabs over one another (cosmetic, as before for neighbouring changes).
- **Limits:** one change per table (no per-row decision); a column change means writing out every row, which a small model may get wrong, and then the refusal above stops it; a table with a margin is still comment-only.
- **Measured on a tool-calling model (2026-10-07, `gemma4:e4b` on Ollama, invented 5-row garden table, four runs per request, the product's own tools and prompt, a change counts only if the resulting note is exactly right):** with the old table rule, adding a row 0 of 4 and removing a column 0 of 4 (the rule told her she could not), one cell 4 of 4, "delete the whole table" 4 of 4 (no change proposed); with the new rule 4 of 4, 4 of 4, 4 of 4, 4 of 4 (16 of 16 against 8 of 16). **Gemini Flash, the same run (invented data only): 0, 0, 4, 4 of 4 with the old rule and 4, 4, 4, 4 with the new, 16 of 16 against 8 of 16.** Not run through `gemma2:9b`, which does not get the table rule.
