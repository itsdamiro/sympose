# 033 — Folder definitions: a note per top-level folder that says what the folder is for and what its notes carry, its template computed from the notes that are there, written only on the user's yes

> **Status: Accepted for stage 1** (2026-09-27; the vault owner chose the template's place and that the health report is where this is offered). Stages 2 and 3 are proposed and get their own measurement before they are built. Settles the design of issue #23; VISION "Folder definitions" is the why.

## Context

A folder called `People` explains itself; `Limbo`, `Code` or `Thoughts` do not, and today nothing in Sympose knows what a folder is for or what its notes should look like. VISION already decides the shape: one definition note per top-level folder, named after the folder (`People/People.md`, Obsidian's folder-note convention), holding the folder's purpose and a frontmatter template, drafted once the folder has real notes and written only on the user's yes. The issue's own words were that this needs an engine and a channel. Both exist now (the terminal chat), but the persona cannot write notes yet (no tool-calling, #21), so the first version cannot be "the persona writes it". The vault owner decided that the vault health report (#77) is where a folder without a definition is noticed and offered, and that what is built now is the function the report, and later the agent, will call.

Three facts about the code as it stands:
- Creating a note in the web app or by `create_note` already applies a template: `Templates/<type> template.md`, matched to the note's top-level folder by name (exact or singular/plural), else `Note template.md`, else a small stub (`vault_write_create.get_template_for_path`). It is keyed by note type and lives in a folder the user maintains by hand.
- A definition note is an ordinary note. The index, the search and the grounding read it like any other, under the `notes` category of ADR 031, and its title (the folder's name) lets the named-note rescue of ADR 030 find it.
- Sympose can only apply a template to notes it creates. A note made in Obsidian bypasses it; checking the notes that exist against it is the health report's job (#77), not this record's.

## Decision

1. **The note.** `<Folder>/<Folder>.md` for a top-level folder, and only top-level folders (the granularity the web app's menu already uses). An existing note is never replaced: writing refuses when the file exists, through `create_note`, which already refuses. Folders that are not the user's content (`Templates`, and the ignored folders of `vault_defaults`) never get one.
2. **What is in it.** A short purpose paragraph, then a `## Template` section holding one fenced code block of property lines (`role:`, `company:`, `email:`). The note's own properties stay free to describe the note itself. The section is found by its heading (whatever the case), the block by being the first fence under it; anything else in the note is the user's and is left alone. The placeholders `{{title}}`, `{{date}}`, `{{time}}` and `{{date:YYYY}}` work as in a `Templates/` file, since the same renderer is used.
3. **The template is computed, not asked of a model.** From the notes in the folder (not counting the definition itself): a property is in the template when at least `folder_template_share` of the folder's notes carry it (proposed default 0.5, a setting), most common first; its value is left empty unless every note of the folder holds the same value (`type: person`), which is kept (a value that only some notes carry is theirs, not the folder's: one person's email must not become the template's). Nothing here can be invented, because every line comes from a count of real notes; that is what keeps the zero-hallucination rule (grounding) intact for this feature. Only the purpose paragraph needs a model (stage 2).
4. **When a folder is due.** A top-level folder with no definition and at least `folder_definition_min_notes` notes (proposed default 5, a setting; the definition is not counted, and a note counts once however deep). A folder that is not due is never nagged about, and nothing is written when a folder is created empty.
5. **Which template wins at creation.** In order: a `Templates/` file made for the folder (the user's own Obsidian setup, and the more explicit), then the folder's definition template, then the general `Note template.md`, then the stub. The general one is for any folder, so a folder's own definition is the more specific. So the two mechanisms cannot disagree about one note. When a definition is drafted for a folder that has a `Templates/` file made for it, the definition's template is that file's property lines, so the two say the same thing.
6. **Written only on a yes, by the caller.** The functions split into a draft (reads the vault, returns the text, writes nothing) and a write (creates the note, from a draft the caller has shown). The caller asks: the health report today, the agent when it can write. A test pins that drafting writes nothing and that writing over an existing definition is refused.
7. **Cloud models.** The purpose paragraph is written from the folder's note titles and sub-folder names (never note text, never a property or its value). Under a cloud model that is content derived from the vault: it is sent only when `notes` is approved (ADR 031, one place decides), and otherwise the draft has the template and no purpose, and says so. A local model is the default and sends nothing.
8. **Seen and hidden.** In the web app's tree a definition note is hidden by default behind a knob to show it, and the persona still reads it (the vault owner, on #23; the general hide feature is #80). Not built here.

**Stages.** 1, built now, no model: find the definition and its template, count a folder's habits, list the folders that are due, render a definition, use its template when a note is created, write a draft. 2, next and measured with the real model first: the purpose paragraph, including when to ask the user instead (only when the titles do not reveal a purpose). 3: the surfaces, in the order the vault owner gave: the health report (#77) offering the draft, the agent (#21) calling the same functions, and the web app's options when a root folder is created (each skippable, nothing forced; #23).

## Consequences

- One artifact serves folder purpose (for the persona) and note shape (for creation), and it is a plain note the user can read and edit, so it travels with the vault.
- Grounding needs no special case for a definition in stage 1; whether a folder's definition should ride along with a note from that folder is a separate question for #78.
- A folder whose notes disagree about their properties (no key reaches the share) gets an empty template section; the draft says so and the user can add lines.
- Editing a definition by hand is safe: only its `## Template` block is read.

## Alternatives rejected

- **The template in the definition note's own properties.** Rejected by the vault owner: the empty `role:`, `email:` lines would also read as the definition note's own properties.
- **A `/folders` command in the terminal chat.** Rejected by the vault owner: the health report is the place that finds what needs attention; the function is what the report and the agent share.
- **Asking the model for the template.** Rejected: it would invent lines; counting the folder's real notes cannot.
- **Keeping the definitions in Sympose's own settings.** Rejected: they would not travel with the vault, and VISION already decided a note.
- **A definition for every nested folder.** Rejected in VISION: noise nobody asked for; extensible if a nested folder genuinely needs one.
- **A stub written when a folder is created.** Rejected in VISION: it guesses blind about a folder that may be an empty placeholder.
- **The definition's template beating a `Templates/` file.** Rejected: the user's own template is the more explicit statement and already works.

## Built: stage 1 (2026-09-27)

`sympose/folder_definitions.py` (reads and computes: `due_folders`, `template_lines`, `read_template`, `template_for_folder`, `render`, and the two settings `folder_definition_min_notes` and `folder_template_share`, each falling back to its default on a malformed value) and `sympose/folder_definitions_write.py` (`draft`, which writes nothing, and `write`, which creates the note through `create_note` and so never over one). `vault_write_create.get_template_for_path` now takes the order of rule 5 (`dedicated_template_file`, then the definition, then `Note template.md`), and only reads a definition the persona may read. No surface is built: nothing calls these yet, the health report (#77) is the first caller.

**Read on the three real vaults (read-only, nothing written; the numbers are counts, not a pass rate).** Personal vault, 619 notes: 7 folders due; the People folder (47 notes) gets `tags, aka, name, created, birthday, email, phone, facebook, up, address` and Movies (28) gets `title, release, genre, watched, rating, recommended by, imdb, created, tags`, the shape those notes really have. Obsidian documentation, 176 notes: 14 folders due, mostly `permalink` and `aliases`. Synthetic vault: 2 due. Nothing in a template is invented, since each line is a count.

**Tests and mutation check.** 70 tests (`tests/test_folder_definitions.py`); 45 mutations of the rules (the minimum and the share at their edges, the order, which folders count, the block and its headings, what is a constant, the draft's refusals, the write's checks, the order of the templates, the scope, the case of a folder), all caught. Two need a case-sensitive filesystem to show and are tested with a simulated one. A first version kept a value as a constant when only some notes carried it (one person's email would have become the template's); the rule is now that every note of the folder holds it.

**Review findings, all fixed.** A folder called `Template` had a note whose own title was read as the section (every `Template` heading is now tried); a `#todo` line between the heading and the block was read as a heading (a heading needs a space after the hashes); the definition was looked up in the exact case typed, while the `Templates/` match ignores case (`folder_named`); a definition outside the persona's folders was read (`allowed_dirs`); and the `create_note` docstring was stale.

**Not built, in the order to take them:** stage 2, the purpose paragraph (one model call from titles and property names, measured with the real model first, `notes` approval for a cloud model, and when to ask instead); stage 3, the surfaces: the health report (#77) noticing a due folder and offering the draft, the agent (#21) calling the same functions, the web app's options when a root folder is created, and the tree's knob to hide the definitions (#80).

## Stage 2: the purpose paragraph (decided 2026-09-27, before the code)

**What it is.** Only the purpose paragraph of a definition needs a model, and it is one call: the same shape as a recap (ADR 023), on the model the user chose (the persona's own, else `chat_model`), with the small helper limit for a local model and room for a cloud one (`helper_limit`, ADR 007).

**What the model is given.** The folder's name, how many notes it holds, up to 40 of their titles (sorted by path and sampled evenly, so a big folder shows its whole range and the same folder gives the same request), and the names of its immediate sub-folders (up to 10). Never a note's text, and never a property, its name or its value: the titles say what a folder is for, the Template section already shows the properties, and anything more would only widen what leaves the machine. (The first version also sent the property names; measuring it with the real model showed why not, see below.)

**What it is asked.** For at most two plain sentences saying what the folder holds, using only what the titles and names show, and for exactly `UNCLEAR` when they do not show it (a folder of miscellany, or titles that share nothing). The instruction lives with the other prompts in `prompt_text.py` (ADR 020). The reply is cleaned like a recap (whitespace collapsed, quotes and a leading label removed, a reply cut by the limit ends at its last whole sentence, at most two sentences kept, `UN CLEAR` read as `UNCLEAR`); a list or headings, or nothing, is treated as none.

**What the caller gets.** A proposal: the draft, and a state of the purpose: `written` (the paragraph is in the draft), `unclear` (the model said the titles do not show a purpose: the caller asks the user for a sentence, and the draft has the template and none), `withheld` (a cloud model without the `notes` approval of ADR 031: nothing was sent, the draft has the template and none, and the caller says so), or `failed` (the model could not be used: the same, and the reason). In none of the last three is anything invented to fill the place. The purpose is a proposal like the rest of the draft: shown, edited by the user if they wish, and written only on their yes.

## Built: stage 2 (2026-09-27)

`sympose/engine/folder_purpose.py` (`propose`, `request`, `clean`, `titles_in`, `subfolders_of`) and the instruction `PURPOSE_INSTRUCTIONS` in `prompt_text.py` (ADR 020). One call on the persona's own model, else `chat_model`, with the helper limit of ADR 007 (120 tokens for a local model); a cloud model without `notes` in `cloud_share` is sent nothing and the proposal is `withheld`. A proposal is `written`, `unclear`, `withheld` or `failed`; in the last three the draft has the counted template and no purpose. Nothing is written by it.

**Measured with the real model** (`ollama_chat/gemma2:9b`, local; the outputs read, not only counted; a fact about this model and these vaults). Three findings, in the order found:

1. **A bug of mine, found only by reading the output.** The first run's paragraph named the real tag values of one folder ("thoughts", "mine", "bio") and listed "person" as a property, although the request held no values. The cause was in the code: when the user has a `Templates/` file for the folder, the draft's template is that file's lines, including its list items and values, and they had been passed on as "property names". The request no longer carries properties at all, and a test pins that no note text, property, value or name from a `Templates/` file reaches the model.
2. **The first wording made things up.** On the personal vault (7 folders, 2 runs each) 12 of 14 replies said something the request did not show: sub-folders that the folder does not have (6 of 14), the properties and tags (10), quoted names that were not given (3), a count of notes (1). With the shipped wording (no counts, no properties or tags, "never call a title a folder") the same 14 runs had none, and the Obsidian documentation (12 folders, 3 runs each) had none in 36. The paragraphs are plain: "These notes are about people.", "The notes in this folder are about coding and software development."; 3 to 9 seconds each.
3. **The model does not reliably say `UNCLEAR`.** On a folder of unrelated titles ("Alpha", "Invoice 0042", "Zebra crossing", "Untitled") the shipped wording gave `UNCLEAR` or `UN CLEAR` in 2 of 9 runs, and two stronger wordings (the decision put first; the rule stated last) gave it in 0 of 8. Instead the model writes an honest but empty "a variety of miscellaneous notes and documents". So `unclear` is a state the code handles and a stronger model may reach, and it is not something to depend on with this one; the proposal is shown to the user either way, and they are the check. A structural signal for an unclear folder (as the vault health report may find) is not built.

**Tests and mutation check.** 34 tests (`tests/test_folder_purpose.py`), 32 mutations of the request, the cleaning, the four states and the single read, all caught but one that is equivalent (`<=` against `<` at exactly the limit returns the same list). Gates: ruff clean, 1604 tests pass.

**Review findings on stages 1 and 2, all fixed.** `#template` (a tag) was read as the heading `## Template`, so its next block became every new note's frontmatter (a heading now needs a space after the hashes, as in Markdown); the health report would have offered a folder that a persona scoped below it could not be given (`due(profile)` now leaves out a folder whose definition exists on disk although the persona cannot see it); the template counted and the titles sent were two reads of the vault (`draft_from`, one read); a list or mapping in `title` or `name` reached the model as a Python repr (only text titles are used, else the file name). The same review found two things in ADR 030's property values: a quoted date or number, or any value of a note whose YAML did not parse (everything is text there), became a name (text with no letter in it is not a value now), and a value hit was recorded as `via: name` (it is `via: value`, in the turn record of ADR 025).

**Not built:** the surfaces, in the vault owner's order: the health report (#77) calling `due_folders` and `propose` and showing the proposal, the agent (#21), the web app's options when a root folder is created, and the tree's knob to hide definitions (#80).

## Update: the web app's options when a root folder is created (ADR 038)

Decided in ADR 038: a skippable setup step after a root folder is created in the web app, starting from a generic template (`title`, `created`, `tags`) instead of a count, writing only what the user typed. It is the one case where a definition exists for a folder that is not due, and rule 4's "nothing is written when a folder is created empty" still holds for anything Sympose would write on its own.
