# 041 — Persona memory: three files, and a rewrite gate by model capability

> **Status: Accepted for the read side (2026-09-29); the write side is still Proposed, unbuilt.** Built: `sympose/engine/memory.py` (`profile`, `context`, `decisions`, `for_turn`), read into every turn the way recaps already are, fixed-priority for `profile.md`/`context.md` and sacrificed oldest-first for `decisions.md` in `budget.fit`, gated by a new `memory` `cloud_share` category, recorded (never as text) in `sent["memory"]`; `HOW_YOU_WORK`'s now-false "you do not learn over time" claim corrected in the same change. Measured against `gemma2:9b` (the shipped local default) — see "Measured" below. Not built: `memory_rewrite`, `/memory refresh`/`review`, `/remember`, the in-turn `remember` tool/marker — none of these write to any file yet, and that half of this record stays Proposed. Amends ADR 011 (supersedes the single `memory.md` it reserved) and ADR 001 (the invariant the gitignore pattern backs, unchanged). Reuses the settings-knob shape ADR 040 already established (`auto`/`ask`) and the cloud-sharing gate of ADR 031.

## Context

VISION defines a persona as soul + memory + expertise + vault-folder scope, and ADR 011 gave memory a reserved path (`profiles/<handle>/memory.md`) without designing what goes in it — "created by the milestones that build them, not now." That milestone hasn't arrived: the dev checkout's `profiles/samantha/` has `persona.yaml`, `soul.md`, `sessions/`, and `recaps/`, but no memory file and no code that reads or writes one.

A real conversation with Samantha (`profiles/samantha/sessions/20260928T151614-f2401cff.jsonl`, cloud model `gemini/gemini-flash-latest`) worked through what she'd want, unprompted by any spec:

- **Transparency over opacity.** Asked to weigh in, she was clear that markdown beats a vector store specifically because the user can open the file and fix or delete a line herself — "you wouldn't be stuck with some mysterious, opaque vector database deciding things behind the scenes."
- **Continuity beyond the current mechanism.** ADR 023 already gives her a short model-written recap of each past session, read at the start of the next. She said she wanted more than that: the recurring threads and how a project evolved over time, not just a rolling per-session summary — "less search engine, more collaborator with a good memory."
- **A structural answer to "quietly updated" docs losing history.** The user's first framing was a single profile doc "quietly updated over time." She flagged the real failure mode herself before it was designed around: a doc that just reflects current state can silently forget you already tried and rejected an approach. Her own fix, when asked how she'd build it, was to split by lifecycle into three files: a slow-changing core profile (working style, defaults, explicit dislikes), an active-context doc (current projects and blockers, cleared out when they wrap), and a dated decision log ("decided against Postgres because SQLite is enough") that exists specifically so a rejected option is never silently retried.

Separately: `samantha.yaml` (the pipx install) already carries `share_memory: true`, predating ADR 031's approval-gated `cloud_share` model — whatever memory ends up holding, sending it to a cloud model needs the same explicit, user-visible control ADR 031 already requires for vault content, not a standing flag from before that rule existed.

And the risk this record exists to gate: whichever file gets rewritten in place (not just appended to) is being asked to do the exact task class local models are worst at — faithful summarization plus a surgical edit without collateral loss — and ADR 007 makes local the shipped default. A bad vault citation is wrong for one reply; a corrupted memory file is wrong on every turn after it, silently, since nothing currently would flag it. That is a structural failure mode, not a per-reply one, and the project's zero-hallucination standard for the vault (ADR 020) has no equivalent yet for memory.

## Decision

Persona memory is three files directly under `profiles/<handle>/`, alongside `persona.yaml` and `soul.md`, replacing the single reserved `memory.md`:

- `profile.md` — stable facts about the user: working style, default tools, how they like to think things through, explicit dislikes. Changes slowly.
- `context.md` — what's active right now: current projects, blockers, open threads. Cleared or archived when a project wraps, so it never accumulates old baggage.
- `decisions.md` — a dated, append-only log of decisions and their reasoning, so a previously-rejected option is never silently re-suggested.

**Writes are gated by mechanism, not treated uniformly:**

- `decisions.md` is append-only, full stop, on any model including local: a new dated line can be added, existing lines are never rewritten. The worst a weak model can do is add one bad line, which is exactly as recoverable as any other line in a plain-text file the user already owns. Because it's already safe on any model, it's the one file written **in-turn**, not only on the lazy refresh below: the model itself can flag something worth keeping the moment it comes up, via the same tool-calling capability check ADR 040 already built — a `remember(text)` tool on models that support tool-calling, or, on any model that doesn't (including the shipped local default, which must not be second-class here), an inline marker in the reply text, `<!-- remember: text -->`, parsed out and stripped before the reply is shown. This is not a new convention: `recap.py` already writes a machine-readable `<!-- turns: N -->` header the same way. Neither path touches `context.md` or `profile.md`. A user can also append directly, unconditionally, with `/remember <text>` — no model call, their own words, for when something must be captured for certain.
- `context.md`'s wholesale rewrite — the one place a weak model can lose or garble existing content, not just add to it — is governed by a new setting, `memory_rewrite` (`auto` or `ask`), the same shape as `vault_lookup` (ADR 040):
  - `ask`: Sympose computes a plain-text diff between the file's current content and the model's proposed rewrite, and writes only after the user confirms it. This needs no tool-calling from the model — the model just writes the proposed new content as text, and Sympose does the diffing — so it works identically on the shipped local default (`gemma2:9b`) as on a cloud model. This is the point: a user running local-only, by choice, is not locked out of a safe rewrite path just because their model would fail some measured fidelity bar. The setting is available to every user regardless of which model they run.
  - `auto`: the proposed rewrite is written directly, no confirmation step.
  - Which value ships as the *default* per model tier is a measurement question (see below); the setting's availability is not.
- `profile.md` behaves like `context.md` in `ask` mode, always, regardless of the `memory_rewrite` setting — it is meant to change rarely and deliberately, so it is either edited by the user directly or written only after the same diff-and-confirm step, never silently, the same "written only on the user's yes" shape ADR 033/034 already use for folder definitions.
- Every write to any of the three files goes through a rolling one-generation backup (`<file>.bak`), formalizing the ad hoc `.bak-<date>` files already sitting unused in the pipx install's `profiles/` directory, rather than leaving that as an incidental, manual artifact.

**Cloud sharing.** Memory content is gated the same way vault content already is (ADR 031): a new `cloud_share` category, `memory`, covers all three files, off by default, told to the user and enabled only through `/share` like `notes`, `properties`, and `recaps`. This retires `share_memory: true` in the current shipped `samantha.yaml`, which predates ADR 031's approval model and is not read as a standing answer — a `decisions.md` line can carry more personal detail than a grounded vault passage ever does, so it gets no less scrutiny than vault content does.

`.gitignore` needs no new lines for this: it already ignores everything under `profiles/samantha/` except an explicit allow-list (`persona.yaml`, `soul.md`), so `profile.md`/`context.md`/`decisions.md` are covered by that existing blanket rule the moment they exist, the same way `sessions/` and `recaps/` already are. Its comment is updated to name the three files in place of the single `memory.md` it used to describe; the invariant ADR 001 records — no persona's memory is ever committed — is unchanged.

**Refresh trigger.** `context.md` and `profile.md` proposals are generated the same way ADR 023's recaps already are: lazily, on a background thread fired at the start of the next session (reusing `recap_refresh`'s existing shape), not at session end — there is no session-end event anywhere in this codebase, and ADR 023 already rejected blocking there for exactly this reason (it once hung `/quit`). The refresh call is fed the handle's recent recap files as input, not raw session transcripts, so it's layered on top of what recaps already compress rather than re-reading whole sessions a second time. `/memory refresh` runs the same job synchronously, on demand, for a user who doesn't want to wait for the lazy trigger.

**Ask-mode review.** A pending `context.md`/`profile.md` rewrite is never surfaced by interrupting the user mid-session — the same reason recaps don't block. It is staged instead, the identical shape ADR 042 uses for a pending vault change: written as a pending proposal and surfaced as a diff the next time the user opens chat (a banner, or `/memory review`), committed only on their yes. `auto` mode skips the staging and writes the proposal directly.

**Budget.** `profile.md` and `context.md` are prioritized near soul/rules in `budget.fit` (ADR 015) — rarely sacrificed, since both are meant to stay small by design. `decisions.md` needs no separate cap invented for it: it goes through the same sacrifice path as everything else, trimmed from its oldest end when it doesn't fit, mirroring how conversation history is already cut — so what survives under pressure is the most recent decisions, the ones most likely to prevent re-litigating something just rejected.

## Open questions (block Accepted status)

- **Which value of `memory_rewrite` ships as the default, per model tier.** Needs the same kind of live measurement ADR 040 ran for tool-calling: real before/after diffs on `context.md` rewrites, across at least one cloud model and the shipped local default, to decide whether `auto` is trustworthy enough to default to anywhere, or whether `ask` is the default everywhere and `auto` is a knob a user opts into knowingly. This decides a shipped default only — the setting itself is available regardless of the outcome.

## Consequences

- Memory becomes a fourth context source alongside recaps (ADR 023), the vault map (ADR 035), and grounded notes (ADR 014/040) — loaded at session start like recaps, not fetched through the `vault_lookup` tools, since it isn't vault content and isn't subject to `vault_folders` scoping.
- A local-only user gets the same safety property a cloud user gets, not a lesser one: `ask` mode's diff-and-confirm step is plain-text and model-agnostic, so it is not a fallback for weak models, it is a first-class option that works identically regardless of `vault_lookup`'s own tool-calling requirement (ADR 040) or which model is running.
- `/settings` (ADR 036) gains `memory_rewrite` alongside `vault_lookup`, and the cloud-share screen (ADR 031) gains `memory` alongside `notes`, `properties`, `recaps`.
- Three new CLI commands: `/memory refresh` (force the lazy `context.md`/`profile.md` synthesis now), `/memory review` (see and act on a pending `ask`-mode proposal), `/remember <text>` (append to `decisions.md` directly, the user's own words, no model call).
- A tool-calling model gains a fourth tool, `remember(text)`, alongside ADR 040's `search_notes`/`open_note` — append-only to `decisions.md`, available regardless of `vault_lookup`'s own `auto`/`ask` setting, since remembering something is not a vault lookup. A non-tool-calling model gets the equivalent via an inline `<!-- remember: text -->` marker in its reply, parsed and stripped before display — the same mechanism `recap.py` already uses for its own `<!-- turns: N -->` header, so the shipped local default is not second-class here either.
- ADR 011's reserved `memory.md` name is superseded by this record; ADR 001's invariant (no persona's memory ever committed) is restated, not changed, and needed no new `.gitignore` line to keep holding.
- The read side is built and tested (2124 tests pass, ruff clean); the write side (`memory_rewrite`, the CLI commands, the `remember` tool/marker, and the default-per-model-tier measurement above) is a separate, later change, gated on this design being settled first — the same order ADR 040 followed.

## Measured (2026-09-29, real model call, scratch data only)

A scratch persona (`profiles/samantha/` under a temporary `SYMPOSE_PROFILES_DIR`, `VAULT_PATHS` explicitly emptied so no real vault was touched) with hand-written `profile.md` ("favorite color is teal... goes by 'Dee'"), `context.md` (a one-line project note) and `decisions.md` (one dated entry), run for real against `ollama_chat/gemma2:9b`, the shipped local default:

- Turn 1 ("what's my favorite color, and what do you call me?"): correctly answered from `profile.md` alone.
- Turn 2, same session ("what am I currently working on, and what did we already decide about storage?"): correctly answered from `context.md` ("According to your active context file...") and `decisions.md` (the SQLite decision), with no vault grounding involved (`vault_folders: []`, confirmed zero grounding hits both turns).
- `sent["memory"]` read back `["profile", "context", "decisions"]` on both turns, matching what was actually sent.

Not measured: a cloud model, the `ask` mode's diff mechanism (unbuilt), and `decisions.md` actually being trimmed under real budget pressure (covered by the unit-level `budget.fit` tests instead, not a live call).

## Alternatives rejected

- **One single memory file, quietly rewritten in full each time** — the user's own first framing. Rejected on Samantha's own follow-up in the same conversation: a doc that only reflects current state loses *why* a past approach was abandoned, which is precisely the failure the decision log exists to prevent.
- **Gating `context.md`'s auto-rewrite behind a measured fidelity bar, with a propose-and-confirm step offered only as a fallback for models that fail it.** This was this record's own first draft. Rejected: it would make a user who runs local-only, by choice, permanently second-class — never able to get a rewrite without either passing an opaque measured bar or being stuck exclusively in fallback mode — when a diff-and-confirm path removes the risk regardless of model and costs nothing to offer everyone as a first-class setting instead.
- **A vector-store or embedding-based memory.** Rejected on the same grounds ADR 002/014 already rejected it for grounding: opaque, not user-editable, and directly against the transparency Samantha herself named as the reason markdown was worth choosing at all.
